# xb-company：公司环境系统

直调契约：还必须读取 `../xbskill/references/contracts.md` 与 `../xbskill/references/resolution-standard.md`；缺失时停止，不得把档案结构写成公司事实已经核验。

读取 `../xbskill/references/agency-model.md`、`../xbskill/references/context-protocol.md`、`../xbskill/references/role-context-model.md`、`../xbskill/references/organization-strategy-genome.md`、`../xbskill/references/intellectual-capabilities.md` 与 [references/company-profile-template.md](references/company-profile-template.md)。任一文件缺失时报告精确路径并停止本专科，不得凭记忆补造理论镜头。模板是机制空表，不代表已初始化。

完整读取 `../xbskill/references/people-domain-patterns.md`，使用四层归因、实际权力账和 M02/M06/M07/M10/M11/M12；文件缺失时报告路径并停止本专科，不得凭记忆补造模式。若只读取一个已确认的公司事实供简单任务使用，可由原专科读取档案，不必触发本专科。

## 核心原则

- 公司不是背景介绍，而是决定“什么建议能落地”的约束系统。
- 公司分析不仅用于适配方案，也用于判断环境能否改变、成本是否被转嫁给个人，以及何时应升级、转岗或退出。
- 把宣称、正式规则、实际运行、当前变化和未知分层，禁止混写。
- 只收集会改变建议的信息；默认不记录客户名单、密钥、个人隐私和不必要机密。
- 国企/央企、民企、外企、事业单位、机关等类别只用于排序候选问题；只有具体实体、适用规则和近期真实案例才能激活策略。禁止从类别推断“慢、乱、扁平、关系化”等文化结论。

## 触发与核心系统模型

公司环境不是“文化好坏”标签，而是五个相互作用的系统：`业务与生存约束 → 组织和权力拓扑 → 正式规则/流程 → 实际激励与 rules-in-use → 当前变化与反馈`。它们共同决定用户能做什么、谁能改变条件、何种行为实际获得资源或惩罚。

P/R/F/I 在本专科中的用法：个人差异 P 和特定关系 R 只作候选；跨人同节点复现增强流程 F；跨期且由权力、资源、奖惩或申诉结构维持才增强制度 I。不得把所有问题都归公司，也不得用“公司一直这样”把制度结果合理化。

## 可观察信号词典

| 信号 | 候选系统断点 | 最小核验 |
|---|---|---|
| 口号/制度要求 A，资源和晋升持续奖励 B | M07 激励冲突 | 近期同口径案例、决定/评价人、时间窗 |
| 组织图的审批人与实际否决者不同 | M11 实际规则 | 两次真实决策链、谁改变结果 |

| “有申诉渠道”但使用后无回应/受损 | M10/M11 | 近期案例、监测、复核、报复证据 |

## 模式与条件分支

1. **最小初始化**：只收集当前任务所需的公司信息。
2. **完整建档**：按模板建立可长期维护的公司环境档案。
3. **任务查询**：读取档案，提取与当前问题有关的约束。
4. **增量更新**：新制度、领导、战略、组织或工具变化出现时追加证据并标记旧信息。
5. **冲突审计**：识别“公司说的”和“公司实际奖励的”之间差异。
6. **任务式交互了解**：围绕一个真实任务逐轮补足会改变动作的组织事实，形成可纠正、可证伪的策略基因；不是首次使用问卷。

条件分支：

- **任务级查询**只返回会改变当前动作的最小字段和未知，不加载全档案。
- **完整建档**必须有明确项目根与用户授权；没有内容时保持“未初始化”，不静默写空表。
- **规则核验**分正式规则、近期真实案例和推断；只有文本不能声明现实有效。
- **归因审计**至少比较个人/关系/流程/制度；没有跨人跨期证据时只保留制度候选。
- **高风险环境**出现骚扰、报复、违法或严重健康信号时，优先保护与专业边界，不用更多组织信息拖延。
- **退出分析**只向 `xb-career` 提供约束和通道证据；公司档案不替用户决定离职。
- **类别种子**只决定优先核验实体/权力/留痕/资金/跨境等哪一项；不得直接激活审批深度、预沟通、总部同意或老板拍板。

## 流程

1. 定位项目根目录和 `memory/xbskill/context/company-profile.md`。目录或文件不存在时明确“公司环境未初始化”，不得静默创建空档案冒充已配置。
2. 若当前只是单一任务，先提取已有事实并判断组织差异是否会改变动作。不会改变就直接返回最小约束；会改变时按 `organization-strategy-genome.md` 每轮只问一个信息增益最高的问题，默认先问最近一次同类事项实际怎样走完。能唯一选择安全动作立即停止，不为完整画像盘问。
3. 完整建档时覆盖模板全部块；涉及采购、签署、正式记录、个人信息、跨境或其他高风险事项时，必须核对实际法律/业务实体、事项适用规则、资金/数据控制主体与有权链，不能用组织类别替代。
4. 每条信息标来源、日期、层级（宣称/正式/观察/推断）和敏感度；推断不得写成公司事实。
5. 从近期案例形成组织基因：每条写 claim、状态（候选/有证据/冲突/过期）、来源/日期、适用范围、动作差异和推翻信号。输出对当前任务的影响：可行、需适配、可协商、结构性受限、禁止、需确认；不得把“公司一直这样”当合理性证明。
6. 先向用户展示“已确认 / 暂定 / 冲突或未知 / 因此怎样调整 / 未采用的类别刻板假设”。只有用户明确授权后才按模板写入；更新采用增量记录，不抹掉历史判断。

## 动作与产物字段

- `最小公司包`：业务/角色、当前目标、关键决定/资源/流程、硬约束、未知、来源/日期。
- `实体与适用包`：实际实体/单位层级、签约/付款/数据控制/记录主体、资金或数据流、适用制度版本、专业复核人。
- `权力流程图`：提出、决定、授权、执行、验收、监测、申诉、改规则及实际案例。
- `宣称—正式—实际对照`：主题、三层内容、证据、影响、置信度、翻转事件。
- `共同/特殊原因表`：结果定义、样本、分布/对照、过程变更、暂定归因、验证窗口。
- `任务影响矩阵`：可行、需适配、可协商、结构受限、禁止、需确认，并写有权者。
- `变更记录`：新事实、来源/日期、生效范围、被推翻旧项、下次重审；不静默覆写。
- `组织策略基因`：决策拓扑、留痕、风险、节奏、激励、沟通、例外、技术/数据约束的 claim、证据、动作差异和反例；公司类别不是基因。
- `交互摘要`：当前已知、激活基因、仍为假设、本轮有意未问、会翻转方案的现实反馈。
- `保存授权`：未初始化/仅读取/待用户确认/已授权更新；敏感字段默认最小化。

## 组织归因闸

判断“环境本身有问题”前，至少取得一条最小事件证据：`发生了什么 + 涉及角色/权力 + 当时正式规则 + 实际做法 + 结果 + 是否重复`。缺少具体冲突、规则落差或报复证据时，只保留条件分支并索取最小事件，不先倾向结构根因。

- 若相同结果跨人员、跨周期出现，并随流程、资源或激励变化，增强系统归因。
- 若断点集中于可追踪的一次异常，且其他人在同流程下未出现，保留特殊事件或个人因素候选。
- 若正式规则可用但现实中无法申诉、监测或修改，记录为“纸面渠道”，不得写成有效治理。

## 理论镜头落地

每题最多选择 1–2 个镜头。

| 理论镜头 | 具体动作 | 写入产物字段 | 失败信号 |
|---|---|---|---|
| 戴明：共同原因/特殊原因 | 统一结果口径，比较跨人、跨期及过程变更；先判断绩效、超载、错误或延期是系统分布还是独特事件，再匹配流程改动或局部处置。 | 结果定义、样本范围、基线/分布、共同原因候选、特殊事件、归因置信度、过程改动、验证窗口 | 单个案例就断言文化有毒；多人多期重复仍归咎个体；过程改动无效却不更新归因 |
| 奥斯特罗姆：实际规则/边界/监测/申诉 | 画实际制度图，分开正式规则与 `rules-in-use`，核对参与边界、决定权、监测、分级处置、申诉和改规则权。分析晋升通道时用近期真实晋升案例验证，而不是只抄制度。 | 参与者/边界、共享资源、正式规则、实际规则、决定权、监测证据、处置、申诉、改规则权、案例日期、冲突 | 纸面制度被当成实际运行；只有传闻却写成晋升规律；申诉渠道存在但无法安全使用仍称治理有效 |

### 晋升通道最小证据

记录 `正式标准、近期实际晋升样本、提名人、决定人、否决点、可见证据、监测/复核、申诉或重审渠道`。只有制度文本时输出“正式通道”；只有个别故事时输出“待验证实际规则”；两者稳定一致后才提高置信度。不得把“领导喜欢某类人”直接写成公司晋升规则。

**微型正例**：制度写“达到等级标准即可申报”，但最近三次晋升都必须由部门负责人提名，员工无自荐入口。将“负责人提名”登记为有三个案例支持的实际规则，同时标明样本窗口和可能推翻它的新案例，再分析用户能否进入提名链。

**微型反例**：用户只说“不敢提问题、最近和同事冲突”，就把公司定性为压制型环境。没有具体事件、正式/实际规则和重复分布时，只能给出沟通、边界、结构三条条件分支。

**边界例**：用户提供一次疑似违法或骚扰事件。它足以触发安全和专业渠道建议，但不足以由本专科作法律定性或推断整家公司文化；也不得为了证明“系统性”要求用户等待更多伤害。

## 验证、失败与翻转

- **事实验证**：每条关键公司信息有层级、来源、日期、适用范围；传闻只能为待验证。
- **机制验证**：用近期真实案例检查权力、审批、奖励、监测和申诉是否按所画规则运行。
- **失败信号**：档案没有日期、口号被当激励、个案被外推文化、正式渠道被当有效、敏感信息过度收集。
- **反刻板失败信号**：仅凭“国企/民企/外企/事业单位”等标签增加审批、假设 HQ/老板权力、套用政府采购或推断沟通文化。
- **翻转条件**：新组织/领导/制度生效；连续案例不符；流程改变后分布不变；纸面申诉现实失效；用户角色或目标变化。
- **停止条件**：缺少必需来源会改变高风险建议、用户未授权保存、或信息收集本身增加泄露风险时，停止相关结论或落盘。

## 输出

公司环境状态、实际实体与适用范围、已知事实、正式规则与实际规则、系统/特殊原因候选、已激活/冲突/过期的组织策略基因、关键约束、决定/监测/申诉结构、当前任务的具体适配差异、缺失但会改变建议的信息、失败/翻转条件、建议保存/更新动作。

模板、制度图、条件分支和待取证清单只算脚手架；未取得现实事件或未获保存授权时，不得声称公司机制已确认或档案已初始化。

现实事件后回流 `原公司假设/模式 → 实际决定/流程/规则 → 真实结果与成本 → 跨人/跨期证据 → 保留/降级/推翻 → 失效旧项与下次重审`。只有用户明确授权才增量写入档案；职业、健康和投诉信息默认不写入公司档案。

## 自检

是否把文化口号或公司类别当真实激励/流程？是否记录了无关机密？信息是否有日期、实体、事项范围与来源？是否一轮一问、够用即停？未知和反例是否显形？保存是否取得用户同意？
