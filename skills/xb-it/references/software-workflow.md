# 小软件制作流程

本流程用于一个人或少量同事使用、范围清晰的工作工具。复用已有工具和组件，以最小维护成本实现用户确认的结果。大型多人系统、复杂权限或高可用部署需要单独评估范围；先交付可独立使用的最小部分，并显形后续依赖。

## 1. 从当前工作进入

先从对话和获准的项目资料提取：谁用、当前怎么做、重复频率、输入、期望输出、最不能接受的错误。保留两个候选：现有功能/模板即可解决，或需要小软件。用一个真实操作片段区分；已有明确软件目标就继续制作，避免重复论证。

开场示例：“这项处理可以做成一个本地工具：选文件后检查并生成结果。先确定输出，随后给你看使用界面。”这只是引导例句，不构成对未知输入的能力承诺。

每轮默认问一个最影响成品的问题，必要时合并最多三个短项。能从当前材料或只读探测取得的信息直接核对。给用户具体结果选项，避免让其选择编程语言或框架。可用的提问顺序按缺口调整：

1. **结果与规则**：一个正常输入应得到什么结果；错误、重复、无法识别的数据如何处理。没有样本时由 Agent 制作明确标为合成的样本，展示预期输出，请用户校准业务规则。
2. **使用环境**：实际使用者的电脑、是否可联网/安装、是否需要发给同事；探测结果区分执行主机和目标电脑。已知条件省去再问。
3. **落地样式**：展示一张简单界面草图或可运行的静态预览，说明用户从打开到拿到结果的操作。提供一个推荐方案及最多两个确有意义的备选，附差别和理由。

需求尚未确认时，可制作无业务副作用的预览与合成测试数据。不得先把未确认的业务规则写成正式实现。

## 2. 一次确认可制作的范围

按 `product-design-test.md` 在工程目录维护一份 `docs/软件方案.md`。小工具合并需求、设计、测试三个章节即可；已有项目沿用其文档结构。不要为了三个 Skill 生成三套重复文档。详细字段用于 Agent 工作，面向用户只展示这张确认卡：

```text
用途：谁使用，哪项工作做到什么程度
输入 → 输出：格式、规模、关键规则和异常处理
界面：入口、主要操作、完成后在哪里取结果（附预览）
运行：目标系统、离线/联网、是否安装、发给同事的方式
本版范围：必做事项；暂不支持且会影响使用的情况
验收：一个正常样本和一个关键异常的预期
```

问“按这个方案制作，还是调整其中一项？”用户可直接说“开始制作”或给修订。若其先前已经明确同意同一份方案且范围未变，记下确认依据并开始。沉默不作确认；“你定技术方案”允许推荐实现，关键业务规则及用户明确要求确认的样式仍需确定。普通可逆实现无需逐步审批。

确认记录包含方案版本、用户原话/消息依据、采用的样式、未决项及其影响。关键规则未决时停止依赖它的实现，其他明确部分可继续；性能或跨平台限制影响承诺时先说明。

## 3. 连续实现、测试与修正

需求确认后自动完成：工程初始化或增量修改 → 核心处理 → 界面与进度 → 错误处理 → 测试 → 打包 → 从交付入口试运行。运行能力和权限允许时持续推进，不在文档完成、计划完成或源码生成后结束。

- 业务处理与界面、文件读写分离，核心规则可直接测试。复用已有可验证代码；禁止把内部数据、作者绝对路径或凭据带进成品。
- 按验收契约先写关键用例，确认它能发现目标错误，再实现并复测。现有功能保留回归样本；源码与打包产物使用相同的合成/脱敏样本核对。
- 长任务提供进度、明确完成状态和错误位置；有取消承诺就实现安全取消。不可中断的阶段明确说明，避免显示无效按钮。
- 默认保留原件并输出新文件；中途失败的临时结果单独标记，不当成正式结果。批处理显示成功、失败和待复核数量，并支持只重跑失败项或给出明确重跑方法。
- 清洗/匹配先展示原值与新值；不确定结果标记待复核，禁止用默认值伪装确定匹配。编码列按文本处理；日期、金额、公式与宏等保真要求逐项核对。
- Agent 自行修复测试揭示的实现错误。用户改变输入、输出、规则、界面主路径或交付平台时回到受影响章节，更新版本和相关测试；未受影响的决定继续有效。

有实际副作用的自动发送、定时任务、生产写入、系统配置、付费服务各按用户已授权范围执行；确认“制作工具”只覆盖确认卡中的动作。企业系统缺接口或访问权时，先做文件导入或沙盒适配，说明尚未连接的部分。

## 4. 交付与完成判定

按 `runtime-delivery.md` 验证实际启动入口。交付至少包括：可运行文件或文件夹、合成示例、简短使用说明、源码/可维护工程、必要依赖及版本说明、测试记录。视平台生成 ZIP，ZIP 根直接放“开始使用”说明和应用入口，避免重复套文件夹。与既有发布方式冲突时沿用项目结构并说明启动位置。

最终答复先给入口链接与最短操作，例如“打开工具 → 选择文件 → 点击处理 → 查看结果”，再说明实际验证的平台、样本和限制。实现细节和完整测试记录放文件链接。需用户亲手操作时按共享 `answer-format.md` 提供编号步骤和预期结果。

内部完成记录使用 `docs/交付验证.md`，至少列出：

| 项目 | 证据 |
|---|---|
| 确认范围 | 方案版本、用户确认依据、变更项 |
| 目标与实测环境 | OS/架构/依赖；是否用户实际电脑；未测试的目标 |
| 实际入口 | 相对路径、运行方式、启动观察 |
| 需求到测试 | 需求 ID → 设计位置 → 测试 ID → 预期/实际 → 证据文件 |
| 结果正确性 | 正常与异常样本、独立计算/规则依据、原件保留情况 |
| 分发与恢复 | 包版本/摘要、干净目录首开、重复运行、旧版恢复方法 |
| 剩余边界 | 未通过/未运行项目、影响、下一动作 |

状态区分：方案待确认、开发中、已构建待验证、已在列明环境验证、用户已试用。只有目标环境的实际入口完成约定任务并通过关键异常检查，才可称“在该环境可立即运行”。仅有源码、编译成功、开发服务器或模型推演时保留较低状态。运行条件受限时明确缺口并交付已完成部分，继续完成不依赖该缺口的工作。

## 5. 试用后的反馈

第一个真实任务检查用户是否找到入口、输入是否接受、结果是否被采用、异常是否可理解；未取得反馈时只声明测试通过。持续收益用用户选择的观察期比较处理时间、复核时间、错误与维护成本；不预设节省比例。需求或环境变化、结果出错、使用成本高于原流程时，更新规则或改用更简单的方式。
