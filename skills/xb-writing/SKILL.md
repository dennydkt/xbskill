# xb-writing：工作写作

直调时先读取 `../xbskill/references/contracts.md` 与 `../xbskill/references/resolution-standard.md`；任何文件缺失时报告精确路径并停止，不得凭记忆补造。事实性内容依赖外部材料时，再读取 `../xbskill/references/knowledge-source-protocol.md`。

文稿依赖数据、技术事实、多人材料，或涉及外发、并发编辑、敏感信息和重复返工时，读取 `../xbskill/references/task-domain-patterns.md`；简单私人草稿不加载。

## 任务定义

工作写作为特定读者建立一个可靠的行动接口。质量按以下结果链检验：

```text
必要信息被正确理解
→ 责任、动作、时间与条件明确
→ 读者能按权限作出回应
→ 误解、返工和用户暴露风险可接受
```

写作可以在本轮解决“形成一份可用文稿”的 Question；是否获得同意、资源、道歉、晋升或关系改变是现实 Problem，必须等待反馈。

## 核心质量模型：读者—动作—证据—边界

| 维度 | 必答问题 | 失败表现 |
|---|---|---|
| 读者 | 谁读、在什么场景读、已知什么、能决定什么？ | 同一稿对所有人说话 |
| 目的 | 希望读者理解、决定、执行或记录什么？ | 只有“同步一下” |
| 证据 | 哪些事实支撑请求，能否定位？ | 用语气强度替代依据 |
| 动作 | 谁在何时做什么，交付到哪里，怎样验收？ | “请相关人员尽快处理” |
| 边界 | 未知、例外、敏感、授权和不处理范围是什么？ | 承诺超出用户权限 |
| 关系成本 | 直接程度与权力、冲突和留痕需求匹配吗？ | 为礼貌隐藏关键请求，或无谓激化 |

每篇文稿优先解决一个主动作。多个动作互相独立时拆段、拆表或拆成多份文稿。

## 信号词典

| 用户说法 | 实际要澄清 | 写作风险 |
|---|---|---|
| “写得专业一点” | 专业体现为准确、结构、证据、术语还是语气 | 堆抽象词和被动语态 |
| “委婉一点” | 要降低冒犯、保留协作还是隐藏拒绝 | 请求和边界消失 |
| “强硬一点” | 要明确事实、截止、责任还是升级后果 | 情绪化、威胁或越权 |
| “简单润色” | 局部措辞还是可改事实与结构 | 覆盖用户已确认内容 |
| “帮我背个书/写正式点” | 谁实际拥有决定权和责任 | 替用户伪造授权 |
| “尽快/高质量/支持一下” | 可观察截止、验收和动作 | 模糊词各自解释 |
| “发给领导” | 领导要知情、决定、资源还是风险预警 | 活动列表代替结论 |
| “留个证据” | 记录事实、请求、确认与时间 | 夹带推测或指控削弱证据 |

## 模式判断

### A. 新写

材料足够时直接成稿。先提取 `已确认事实、用户判断、期望动作、不可写内容、格式与截止`；只有缺失信息会改变事实、授权或主动作时才问一个关键问题，否则用显式占位符或条件分支。

### B. 整体改写

保留事实、专名、数字、引用与用户意图；区分“表达问题”和“内容问题”。删空话不能删必要的关系缓冲，重组结构不能把推断升级为事实。

### C. 局部修改

重读当前版本，把用户点名范围外内容设为硬锁。只改词、句、段或语气目标；检查相邻逻辑和全文目标词，不恢复用户删掉的内容。文件出现外部修改时停止覆盖并重读。

**硬锁不等于事实授权**：锁定句只证明“用户要求逐字保留”，不证明句中事实、制度、薪酬或对他人权益的承诺已经获有权者确认。对外通知出现这类句子时建立两账：`文字锁（原文/范围/逐字校验）` 与 `事实授权（来源/有权确认人/状态）`。文字必须原样出现在草稿中；事实授权缺失时同时标“仅草稿、不得发布”，不能为了安全偷偷改句，也不能因不能改句就把未核实承诺正式外发。

### D. 忠实整理

用户只要排版、转录、合并或归类时，不擅自纠错、补事实或改变立场。发现明显冲突，以批注或冲突账单列，不静默“修正”。

## 文种分支

| 文种 | 默认信息顺序 | 必备动作字段 |
|---|---|---|
| 邮件/即时消息 | 结论或请求 → 必要背景 → 动作与截止 → 附件/联系人 | 收件人、动作、时间、回复方式 |
| 通知 | 变化 → 适用对象 → 生效时间 → 操作 → 例外/支持 | 谁受影响、从何时、必须做什么 |
| 方案 | 目标 → 现状证据 → 选项/取舍 → 推荐 → 资源与决定 | 决定人、成本、风险、验收 |
| 制度/流程 | 目的与范围 → 角色 → 触发 → 步骤 → 例外 → 申诉/更新 | 权责、证据、例外、版本 |
| 说明/FAQ | 对象定义 → 使用条件 → 步骤 → 结果 → 故障/边界 | 前置条件、完成信号、失败入口 |
| 申请/升级 | 请求 → 依据与影响 → 已做动作 → 所需支持 → 截止 | 有权者、最小资源、无支持后果 |
| 总结 | 目标 → 结果证据 → 偏差 → 决定 → 下一步 | 活动/结果分离、未完成项 |

不要为套模板补无关章节。读者只需一条消息时，不扩成报告。

## 写作动作

1. **建立写作卡**：读者、场景、主动作、决定权、已知/未知、敏感点、载体、长度和截止。
2. **建事实账**：把内容标为已证实、用户确认、推断、待确认、已失效；关键事实挂来源。
3. **选信息顺序**：先放读者行动所需内容，再放解释；高权力差场景保留必要事实与书面确认。
4. **具体化**：用明确主语、动词、对象、数字、时间、条件和验收替换“加强、赋能、尽快、相关、原则上”。
5. **控制承诺**：只承诺用户能控制的动作；对他人行为写请求、依赖或待确认。
6. **匹配语气**：中性直接为默认；礼貌不删除边界，强硬不添加未经授权的后果。
7. **保护当前文本**：文件修改按共用改动保护；用户亲自确认的句子优先于默认文风。
8. **交付成稿**：默认只给一个可直接使用版本；变体必须对应真实场景差异，不堆三个同义版本。

## 产物字段

```text
写作模式与文种：
读者、场景与决定权：
主目的与希望动作：
事实来源 / 推断 / 待确认：
必要背景与不披露内容：
责任主体、动作、截止、验收：
语气选择及关系风险：
锁定文字与修改范围：
锁定文字的事实授权：来源 / 有权确认人 / 待确认或已确认
可直接使用成稿：
发送前用户复核点：
现实反馈与翻转条件：
```

最终成稿不必展示内部字段；但事实、动作、截止、未知和边界中适用项必须在文中可见。

## 默认禁用

用户未要求时，不加入营销钩子、痛点渲染、虚构读者经历、最高级、口号、无来源效果承诺、人格判断和情绪代言。不为显得“会沟通”过度道歉，不用“我司高度重视”等句子替代实际动作。不把用户合理的拒绝改写成含糊承诺。

## 案例校准

**正例**：用户要提醒协作方补材料。成稿先写缺少的三项、对应项目、提交位置和周三 15:00 截止，再说明缺失会影响周四评审；无法按时请在周二下班前回复可交日期。它没有指责，也没有隐藏影响和反馈动作。

**反例**：“为了进一步赋能项目高质量推进，请相关同事尽快给予大力支持。”读者不知道谁做什么、何时完成、怎样算完成；礼貌和抽象词掩盖了接口。

**边界例**：用户要求写“领导已经批准”，材料只有领导说“先看看”。不能替用户强化授权；可写“已与领导初步沟通，现提交供确认”，并把正式批准列为待确认。

**硬锁边界例**：用户要求通知中的“本次调整不影响现有奖金”一个字不能改，但制度细节和薪酬授权均未提供。交付可保留该句的正式草稿与待补字段，同时明确“锁句已保护、奖金承诺未获事实授权、当前不得发布”；只有薪酬/制度权责人书面确认后才进入外发复核。

## 验证、失败与翻转

- 读者在 30 秒内不能说出发生了什么、自己要做什么和何时做：重写信息顺序。
- 关键事实无来源或材料冲突：改为待确认/条件句，不能润色成确定事实。
- 用户只要求局部修改却产生范围外差异：判交付失败，恢复并重做。
- 语气调整后主请求、边界或责任消失：语气方案失败。
- 文稿可发送但需用户确认收件人、数字、附件、承诺或敏感信息：标“成稿已交付，外发未授权”。
- 对方现实回应与预期不符：先检查事实、权限、利益和渠道，不把失败一律归为措辞不够好。

## 结果回流

只记录对改进有用的反馈：读者是否按预期理解、追问集中在哪、是否返工、哪处承诺或边界失真、用户保留/删除了什么。反复被误解的字段进入模板；反复被用户删除的默认写法退出。写作净收益以减少澄清、返工和暴露风险为准，不以字数、正式程度或一次性好评代替。
