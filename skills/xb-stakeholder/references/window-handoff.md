# 对外窗口的接手校准

本文件只用于用户承担外部沟通、实际处理另有负责人的情形。沿用当前专科的角色地图、承诺账与权限规则，不增设第二套台账。用户也有订单核对、材料补齐等实际职责时保留本人部分；外部催促本身不能证明内部失职。

## 状态与最小事实

每件事项在原承诺账附上：外部要求与原话、内部已确认范围、用户可控制动作、处理人、决定人、下一反馈时点、状态证据、无回应出口。

状态按证据更新：`已收到 → 待接单 → 已确认接单 → 处理中 → 待验证 → 已解决`。另保留拒接、缺材料、缺资源、超时与重开。群内“收到”和已读只证明接收信息；接单须有具体人明确承担的动作和反馈节点。已解决须有处理结果、约定验收及仍受影响范围；AI生成请求不改变现实状态。

先辨别“已处理但信息未同步”和“确实无人承接”。向可核对的处理接口索取一次状态依据；禁止仅据沉默推定动机。窗口可以承诺自身可兑现的进度更新时间，恢复、赔偿或上线日期需相应有权者确认。

## 拒接与期限

- 拒接：核对权限、材料或资源原因，携带具体缺口请求有调度权者决定。缺材料且属于本人职责时先补可授权部分；不得把全部任务推回。
- 超时：记录哪项已确认节点未兑现，向已核实的协调接口请求裁决；只给出有依据的外部更新，不把“已升级”当资源落实。
- 无可用协调人：保留“未完成交接”，输出当前可承担部分、无法承诺部分、待有权者裁决及下一反馈。不得凭空指定负责人、无限重复催促或替用户宣布交接完成。
- 先前对外过度承诺：回查确认来源与最新状态，准备事实修正稿；对内核对责任，对外保留必要信息，避免传播内部指控与日志。

## 回归样本

正例：客户要求16点恢复接口，研发只回“收到”。交付接单请求和客户进度稿；内部未给技术依据时恢复日期保持未知。反例：研发已完成处理并给验证记录，只遗漏抄送；转为同步与验收，停止催接单。边界：窗口有订单核对权限却未核对；先完成本人可做部分，修系统与赔偿仍待有权者。

检查：内外日期来源一致；接单与已读分开；当前状态有原文证据；拒接及超时有可执行出口。下一次实际回应推翻原状态时及时更新；确认接单可解决交接瓶颈，业务故障仍需验证。
