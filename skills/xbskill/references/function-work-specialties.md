## 1. 适用范围与共同闭环

本图谱覆盖项目管理、行政、秘书和综合办公室/机关办公室。岗位上下文不新增菜单，当前瓶颈仍进入 `xb-goal`、`xb-plan`、`xb-meeting`、`xb-writing`、`xb-decision`、`xb-company` 等现有专科。

当职能事项需要更细的专业观察、竞争解释、权限分支、记录产物或现实验收时，由已选定的当前专科支持调用 `xb-role-knowledge`，只匹配本轮角色/任务单元并形成作用轨迹。企业类别不参与专业匹配；正式规则仍需当前实体、事项和有权真源确认。

```text
需求/事项接收
→ 实体、权限、风险与适用规则分类
→ 准备、计划与协调
→ 文稿、会议、记录或资源办理
→ 审核、批准与执行
→ 服务交付、督办或事件响应
→ 验收、归档与审计证据
→ 复盘、规则改进或退役
```

“发出通知、开完会议、提交报告、流程显示办结”只是产物状态。现实闭环还要区分是否形成有效决定、责任人是否承诺、服务对象是否收到结果、异常是否关闭、规则是否真正改善。

## 2. 四岗位责任边界

| 岗位 | 对结果的专业责任 | 不能默认拥有的权力 |
|---|---|---|
| 项目管理 | 目标/范围/计划/依赖/风险/信息/变更/收益反馈，促成有权者决定 | 不因“项目经理”头衔自动拥有资源、预算、合同、范围或人员决定权 |
| 行政 | 服务请求、会务/活动/差旅、物资资产、供应商、文件记录、连续性与服务改进 | 不替采购、财务、法务、档案、保密或业务 owner 作专业裁决 |
| 秘书 | 指令澄清、日程/议程、材料、纪要/决定、督办、关系与保密边界 | 不替领导表态、承诺、签署或作决定；“秘书”必须先辨普通秘书与法定职务 |
| 综合办公室 | 综合信息、公文、督办、印章/授权/档案/保密接口、行政资源、值班事件 | 不因“办公室牵头”取得所有事项最终权；制度适用由实体、事项和有权规则决定 |

若用户是上市公司董事会秘书、特定机构法定秘书、机要秘书等，必须单独锁定官方职责和适用规则；不得套普通行政秘书图谱继续。

## 3. 岗位 × 阶段矩阵

### 3.1 项目管理

| 阶段 | 代表任务与可观察证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 在指导下形成需求卡；任务有唯一 owner、截止、依赖；会前目标/材料、会后决定/行动齐全；记录谁何时决定什么；异常及时升级 | 计划只有任务名；把催办当管理；未经授权承诺资源/预算；会议纪要混淆讨论与决定 |
| S1 入门/独立常规 | 独立分开目标、范围、验收、约束和不做项；维护基线、容量、风险、预测与变更；识别权力/利益并取得真实承诺；事件遏制—恢复—复盘闭环 | 只报完成率不报预测；范围/资源/期限都固定却归因执行力；风险表不触发动作 |
| S2 老手/复杂系统化 | 建立项目/组合入口、价值筛选和停止门；跨项目容量与情景规划；设计决策节奏、治理/保证、采购/供应商和收益实现回流；验证控制净收益 | 治理门吞掉交付；组合只做项目汇总；“按流程”掩盖无权决定或无现实收益 |

### 3.2 行政

| 阶段 | 代表任务与可观察证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 登记服务对象、需求、期限、标准和缺口；按清单完成会务/差旅；物资领用归还、票据和文件版本完整；按预案报告异常 | 靠记忆接单；材料齐全但对象/权限错；普通网盘冒充档案系统；先替他人承诺再补流程 |
| S1 入门/独立常规 | 独立分流、排队、例外和恢复；管理多方依赖、供应商、取消、无障碍/安全与备用；做库存阈值、比选、验收、记录移交；协调共享真源 | 只追求响应快而不分优先级；供应商交付与验收混同；例外无 owner、无结束条件 |
| S2 老手/复杂系统化 | 建服务目录、容量和指标；设计活动/供应商/资产/记录全生命周期、授权分离、审计抽查、连续性演练和接口治理；验证成本、质量和采用 | 过度流程化低风险请求；自动化错误被规模化；制度覆盖率替代服务结果 |

### 3.3 秘书

| 阶段 | 代表任务与可观察证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 复述对象、意图、交付、时限和保密；日程/参会人/材料准确；纪要分讨论、决定、待定、行动；文稿来源/受众/动作/事实清楚 | 把含糊口头要求自行定稿；用领导口吻作无授权承诺；纪要把建议写成决定 |
| S1 入门/独立常规 | 区分信息、建议、请示、决定和代办；识别决策事项并会前协调异议；核对决定权、条件、版本和变更；多材料交叉核验并管理敏感接触 | 日程优化压过真正优先级；预沟通变成泄密/操纵；督办只有催促无依赖处理 |
| S2 老手/复杂系统化 | 建领导工作入口、授权和失效提醒；围绕决策节奏配置注意力；建立决定账、督办阈值、废止关系、信息架构、证据链和交接规则 | 个人不可替代成为单点；“领导习惯”固化为永久规则；保护领导被扭曲为隐瞒事实 |

### 3.4 综合办公室/机关办公室

| 阶段 | 代表任务与可观察证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 汇总事实/来源/未知；按适用格式、签发、传递和保密流程办文；登记决定、责任和期限；印章/授权/档案只按批准操作；准确接报和值班交接 | 传闻写成结论；企业内部通知套机关公文规则或反之；印章先用后批；办结等于落实 |
| S1 入门/独立常规 | 形成议题、选项、影响、会签/请示材料；协调核稿、版本、反馈、归档；识别延期原因/依赖/升级；协调预算、招采、合同、供应商和资产入账接口；事件恢复与复盘 | 办公室牵头即替专业部门决定；多个版本无权威真源；督办制造虚假完成 |
| S2 老手/复杂系统化 | 设计信息上行、议题筛选、决策支持、决定—执行—复核；建立公文质量/时效/安全治理、职责分离、抽查/应急、资源组合和跨单位事件机制 | 中枢化吞噬部门责任；所有事项一律最高留痕；治理指标与现实服务/风险脱节 |

## 4. 职能工程对象

### 4.1 事项/服务入口卡

```text
提出者/服务对象｜目的和预期结果｜交付物｜期限/时效等级
实体与事项类型｜所需决定｜用户责任/权限｜材料缺口
失败后果｜不做项｜受理/退回/升级理由
```

### 4.2 权力与责任图

```text
提出｜咨询/会签｜决定｜正式批准/签发｜执行｜验收｜复核/申诉
承担后果｜实际否决点｜授权依据与期限
```

不能用一个模糊的“负责人”覆盖所有动作。用户无权改变范围、资源或期限时，计划必须把决定交给有权者，不能写成用户的执行力问题。

### 4.3 计划与变更卡

```text
目标/范围/验收｜基线｜工作包/唯一 owner｜容量｜依赖
风险触发器/应对｜决定门｜变更请求/影响/决定｜预测｜收益反馈
```

### 4.4 会议与决定包

```text
会议类型：信息/讨论/决定/批准
目标｜有权参会者｜议程/预读/版本｜异议与待决项
讨论｜决定｜条件｜待定｜行动/owner/日期｜分发/归档｜废止关系
```

### 4.5 文稿/简报证据包

```text
受众｜希望理解/决定/行动｜事实与来源｜观点/建议｜选项与影响
需会签/签发处｜敏感度｜版本｜适用范围｜未核实项｜反馈入口
```

### 4.6 资源/采购/资产链

```text
实际实体｜需求与资金来源｜预算/权限｜采购方式/职责分离
比选/利益冲突｜合同接口｜收货/验收｜付款接口｜入账/领用/归还/处置
```

是否适用政府采购、集团招采或其他规则，必须由实际主体、资金和当前有效制度判定；不得只看“国企/事业单位”标签。

### 4.7 事件响应包

```text
时间线｜影响/受影响对象｜当前状态｜事件负责人/各方角色
遏制｜恢复｜沟通｜决定和行动日志｜证据保护｜交接
复盘发现｜行动项/owner/截止/验证｜后续事件效果
```

### 4.8 记录与归档索引

```text
记录类型｜业务语境｜权威版本｜形成者/批准者｜日期
权限/敏感度｜元数据｜保留/移交/处置依据｜位置｜审计事件
```

AI 不决定法定保留期，不提供规避审批、销毁证据或绕过审计的方案。

## 5. 重点场景检查面

### 项目延期

先比较基线与当前预测，定位范围、容量、依赖、决定延迟、质量返工和外部事件；列用户能改与不能改的变量；向有权者提交事实—影响—选项—所需决定—截止点。不能把所有偏差归“执行力”，也不能只催责任人。

### 会后大家理解不一致

核对会议类型、决定权和当时材料版本；把讨论/建议/决定/条件/待定/行动分账；由有权者确认争议决定；追加修订和废止关系，不静默改写原纪要。

### 领导口头交办含糊

用一句话复述对象、意图、交付、时限和保密；若涉及对外承诺、资源或正式决定，必须让有权者选择；秘书可先准备草案/选项，不能自行把语气补成授权。

### 临时重要接待或活动

建立目标、参与者、场地/交通/供应商、预算权限、无障碍/饮食/安全、材料、通讯和取消条件；设置 T-1/T-0 核验和备用路径。敏感人员信息最小化，清单不等于权限。

### 采购需求“很急，先买再补”

先查实际实体、资金、权限、现行采购制度和紧急例外；无合法例外时停止承诺，给替代租借/库存/范围/时间选项；有例外也要由有权者批准并补齐记录、验收和利益冲突控制。

### 正式公文还是普通内部通知

判断实际主体、受众、是否行使正式职权、是否进入法定/正式公文办理；只有命中适用范围才锁定相应官方文种/格式版本。普通协作保持轻量，党政机关规则不能默认复制给企业。

### “秘书”角色歧义

先问是领导/行政秘书，还是上市公司董事会秘书等法定职责。后者涉及公司治理、会议文件、股东资料和信息披露等正式责任时，必须读取当前官方规则和公司章程，不继续使用普通秘书模板。

### 突发事件复盘

先区分报告已完成、行动项已实施和现实风险已下降。后续结果未发生时只能写“已建立干预和观察窗”；不以一次培训或“加强意识”关闭系统性问题。

## 6. 组织适配与法规门

按 `organization-strategy-genome.md` 逐轮识别。职能任务优先核验：

1. **实际实体和单位层级**：谁签、付、控制数据、形成记录、承担责任？
2. **权力链**：谁提出、决定、批准、执行、验收、复核？正式与实际有何差异？
3. **适用规则**：当前事项是否命中公文、档案、采购、预算、合同、印章、保密、个人信息或跨境门？
4. **资金与资源**：资金来源、阈值、采购主体、验收和利益冲突怎样规定？
5. **最近案例**：上一次同类事项实际经过谁、耗时多久、在哪被否决或例外？

类别只调整核验顺序。例如央国企先核对具体企业层级、事项清单与最终权责；外企先核对本地/HQ 权力和数据流；事业单位先核对主管部门、资金与事项适用规则。没有证据不得直接激活“多审批、预沟通、总部同意”等动作。

## 7. 路由、验收与越权保护

- 需求受理、结果和验收 → `xb-goal`；项目基线、依赖、容量、变更 → `xb-plan`。
- 会议类型、议程、纪要、行动 → `xb-meeting`；文稿/请示/简报/通知 → `xb-writing`。
- 权责、多方、领导和升级 → `xb-company`、`xb-stakeholder`、`xb-upward`。
- 取舍和决定账 → `xb-decision`；流程自动化 → `xb-automation`；材料复核 → `xb-review`。

硬边界：未经明确授权，AI 与用户都不因岗位名称自动获得外发、批准、签署、盖章、采购、付款、用印、销毁、改变正式记录、代表领导/组织承诺的权限。可以准备草案、核验包和待决选项，必须把最后动作留给有权者。

交付检查：

1. 是否辨清实际实体、角色词义、事项类型和适用规则，而非按单位标签套流程？
2. 是否分开提出、决定、批准、执行、验收、复核和后果承担者？
3. 是否让阶段改变操作粒度和验证方式，而非按工龄贴标签？
4. 是否把会议/文稿/流程办结与现实决定、服务结果、风险下降分开？
5. 是否有权威版本、变更/废止关系、异常/例外 owner 和现实反馈点？
6. 是否只增加覆盖具体风险的控制，避免过度文书和过度会议？
