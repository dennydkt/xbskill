# 任务型专科共用模式

本文件服务 `xb-it`、`xb-data`、`xb-automation`、`xb-writing`、`xb-presentation`、`xb-report`、`xb-review`。只有任务跨两个以上专科、交付链较长，或出现证据冲突、权限风险、外部修改、重复返工时才读取；简单单专科任务不要为完整性加载。

它提供共用机制，不代替各专科的领域判断。若本文件与 `contracts.md`、`resolution-standard.md` 或公司正式规则冲突，以顶层契约、安全边界和有权者的有效规则为准。

## 1. 最小主张链

任何会影响决定、外发或后续自动化的结论都保留以下链条：

```text
来源 → 可定位证据 → 处理/转换 → 主张 → 适用范围 → 决定或动作 → 验证反馈
```

链条的每一段回答不同问题：

| 节点 | 必答问题 | 常见失败 |
|---|---|---|
| 来源 | 材料由谁、何时、按什么版本产生？ | 只写“业务提供”或“网上查到” |
| 证据 | 陌生人怎样重新定位？ | 只有截图、转述或无坐标摘录 |
| 转换 | 做了哪些筛选、清洗、计算、改写或格式变换？ | 中间步骤不可复现 |
| 主张 | 证据具体支持什么，不支持什么？ | 从局部证据跳到整体结论 |
| 范围 | 对象、时间、版本、条件和例外是什么？ | 省略限制，标题说得比正文更强 |
| 动作 | 谁基于主张做什么，谁有权确认？ | 建议没有主体或越过授权 |
| 反馈 | 什么现实结果会确认、修正或推翻？ | 交付文件后就宣布问题解决 |

主张链断裂时，不要用更流畅的文案掩盖。把断点写成待取证项、假设或阻塞项。

## 2. 事实状态与冲突账

不要把材料中的每句话都当成同等事实。给关键内容标一个状态：

- `已证实`：存在可定位的一手材料，且范围、版本适用；
- `用户确认`：由用户明确提供，当前任务可用，但未必是组织真源；
- `推断`：由证据推导，写出依据与置信度；
- `待确认`：缺少会改变结论的信息；
- `已失效`：被新版本、现实结果或有权决定替代，保留演进关系。

材料冲突时建立冲突账：

| 冲突主张 | 来源 A/日期 | 来源 B/日期 | 影响范围 | 临时处理 | 有权裁决者 | 截止/触发 |
|---|---|---|---|---|---|---|

在裁决前可以继续做不依赖该冲突的部分；依赖冲突的结论必须停止或写成条件分支。不要以“更新的文件”自动胜出，除非版本规则或有权者确认如此。

## 3. 风险与权限闸门

先判断动作的外部副作用，再决定是否执行：

| 等级 | 典型动作 | 默认处理 |
|---|---|---|
| R0 只读 | 查看日志、读文件、统计、草拟、不外发 | 可直接做，仍最小化敏感信息 |
| R1 可逆本地改动 | 新建副本、局部格式修改、沙盒脚本 | 记录改动与回滚点后做 |
| R2 有限共享或批量改动 | 发给明确收件人、批量改文件、更新共享草稿 | 复述范围、样本验证、取得确认 |
| R3 外部或生产副作用 | 正式外发、提交、改权限、定时运行、生产写入 | 明确授权、审计日志、人工闸门、回滚/停用 |
| R4 难逆或高影响 | 删除、付款、签署、公开发布、影响多人权益 | 不替用户授权；逐项复述目标、对象和影响后确认 |

“有技术权限”不等于“有业务授权”。至少区分提出、决定、执行、复核和承担后果的人。涉及公司机密、个人信息、薪酬、健康或绩效时，默认脱敏并按最小必要披露。

## 4. 改动保护与并发编辑

编辑文件、代码、数据或文稿前：

1. 读取当前版本，记录路径、版本/修改时间和目标范围；
2. 标记用户锁定内容、受保护公式、格式、接口和下游依赖；
3. 把原件与工作副本分开；用户明确要原位修改时仍先形成可恢复点；
4. 一次只改变一个主要变量，或把多项机械改动列成可审计变更集；
5. 修改后重新读取目标和相邻区域，比较范围外差异；
6. 发现外部并发修改时停止覆盖，重读并合并，不凭先前记忆回写。

交付变更账：`对象/位置、修改前、修改后、理由、授权、验证、回滚点、未触及范围`。

## 5. 最小验证矩阵

不要只测顺利路径。按任务风险选择样本，不机械凑全：

| 样本 | 检查什么 |
|---|---|
| 正常 | 典型输入能否得到预期结果 |
| 边界 | 空值、最大/最小值、跨期、特殊格式、临界听众 |
| 错误 | 缺字段、无权限、坏格式、冲突指令是否响亮失败 |
| 重复 | 重跑、重复导入、重复发送是否产生重复副作用 |
| 负例 | 本不应命中、修改、纳入或通过的对象是否保持不变 |
| 恢复 | 中断、回滚、重启或换人后能否恢复到可解释状态 |

验证记录至少含：`版本/环境、样本、预期、实际、证据位置、结论、失败后的动作`。没有执行验证时只能写“验证方案已交付”，不能写“已验证”。

## 6. 结果回流卡

交付物完成后，用最小回流卡防止下次从零开始：

```text
本轮目标与受众：
已交付对象及版本：
已验证到哪一层：文件 / 流程 / 现实结果
用户侧净变化：节省时间、减少返工、提高可见性、降低风险或增加选择中的哪一项
新增成本：维护、认知、等待、协调或风险
未解决部分：
下一反馈事件与负责人：
会推翻本轮判断的证据：
可沉淀规则/模板/能力证据：
```

只在现实反馈出现后填写现实效果。估计节省时间时分开记录基线、预测和实测，不把预测写成收益。

## 7. 三个跨专科案例

### 案例 A：月报数字与系统不一致

- `xb-data` 先固定指标口径并定位差异来自时间窗和去重规则；
- `xb-report` 将旧结论标为已失效，保留新旧口径及影响；
- `xb-presentation` 只在管理层页面放当前可决策数字，附录保留对账证据；
- 若每月重复，`xb-automation` 在口径由有权者确认后再自动对账。

**错误迁移**：先让 `xb-writing` 把差异解释得更顺，或在口径未定时直接自动化。文字流畅和自动运行都会放大未解决的主张链断点。

### 案例 B：批量转换文件后正式外发

- `xb-it` 确认格式、兼容性和原文件保护；
- `xb-automation` 在副本上完成批量转换并跑正常、边界、错误和重复样本；
- `xb-review` 抽查内容、命名、收件范围与敏感信息；
- 正式外发仍是独立的 R3 权限闸门。

**边界**：脚本成功不等于文件内容正确，更不等于获得外发授权。

### 案例 C：领导要求“做一页专业的方案”

- `xb-writing` 先把“专业”转成读者、动作和验收项；
- `xb-data` 核对关键数字的口径与范围；
- `xb-presentation` 让该页只承担一个决定；
- `xb-review` 用一个会推翻主张的反例做交付门。

**边界**：若领导只要材料存档而非作决定，不要强行套决策型演示结构。
