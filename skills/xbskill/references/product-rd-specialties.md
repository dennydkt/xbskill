## 1. 适用范围与共同生命周期

本图谱覆盖产品经理、UX 设计师、前端工程师、后端工程师和架构师。入口仍按当前瓶颈进入一个现有专科；岗位图谱只调整检查面、责任接口和答案深度。

当具体专业问题需要更细的观察、竞争解释、辨别动作、分支、产物或验证时，由已经选定的当前专科支持调用 `xb-role-knowledge`，只匹配本轮责任帽子与生命周期切片并形成作用轨迹；普通任务中它不成为第二个当前 Skill。

```text
机会/探索
→ 问题定义与研究
→ 范围、结果和验收
→ 体验/服务设计
→ 架构、API 与数据合同
→ 实现和验证
→ 发布、迁移与回滚
→ 运行、观测与事故
→ 学习、迭代、规模化或退役
```

PRD、设计稿、代码、测试通过和部署成功都是中间产物，分别不等于用户问题或业务结果已改善。每一阶段都设置现实反馈点和继续/改变/停止门。

## 2. 五岗位责任接口

| 岗位 | 对结果的专业责任 | 不能默认拥有的权力 |
|---|---|---|
| 产品经理 | 用户/业务问题、结果、优先级、范围、生命周期与证据闭环 | 不替 UX 宣称用户事实，不替工程决定实现，不替授权人批准商业上线 |
| UX 设计师 | 用户研究、旅程、交互/内容、包容与可访问体验证据 | 不替业务批准目标，不因设计稿完成宣称体验有效 |
| 前端工程师 | 客户端实现、状态、兼容、性能、可访问性、用户侧观测和发布证据 | 不独自改变产品语义、API 合同或风险接受 |
| 后端工程师 | 领域/API/数据实现、一致性、可靠性、安全、成本、恢复证据 | 不替产品定义价值，不替安全/业务 owner 接受剩余风险 |
| 架构师 | 跨系统质量属性、演进路径、权衡、例外与系统性风险建议 | 是否审批取决于组织制度；不能靠架构图替代团队验证和运行结果 |

上线时具名区分提出、咨询、决定、批准、执行、复核和承担后果者。安全、隐私、无障碍、运维、法务等专业责任人命中风险时进入复核，但不预设所有事项都需要最高强度门禁。

## 3. 岗位 × 阶段矩阵

### 3.1 产品经理

| 阶段 | 代表任务与证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 把已给需求写成用户/问题/范围/验收；维护 backlog、澄清和 UAT；发布清单注明 owner、观察窗、停止/回滚；亲自核验一条用户反馈 | 把功能、PRD 或上线当结果；没有 no-build 门；验收只写“正常” |
| S1 入门/独立常规 | 交叉核验访谈、行为、客服、法规和业务约束；以价值/风险纵向切片；组织可用性、功能、护栏验证；联合结果、可靠性、成本和分群数据更新假设 | 单一指标即成功；变更挤压质量；使用量等于价值；发布后无 owner |
| S2 老手/复杂系统化 | 管理机会/产品组合与战略取舍；协调多团队、预算、架构和运营准备；建立 SLO/信任/组合健康机制；扩、改、停、退役并重配投入 | 路线图成为承诺堆；所有问题都建设；组织机制掩盖用户证据 |

### 3.2 UX 设计师

| 阶段 | 代表任务与证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 整理观察/访谈；按现有模式画完整状态；交付内容、响应式和无障碍标注；做启发式、视觉和真实旅程走查 | 只有理想路径；审美替代用户证据；套组件即宣称可访问 |
| S1 入门/独立常规 | 独立研究并交叉验证行为、语境和可访问需求；设计旅程/状态/原型；与前端共定义组件合同；主持可用性、辅助技术、跨设备和边界测试 | 招募样本不代表关键用户；研究结论无反证；交付后不看实现和运行反馈 |
| S2 老手/复杂系统化 | 建立持续研究、伦理招募和弱势用户覆盖；治理设计系统、贡献门、迁移和废弃；识别模式债务与长期排除；验证多团队采用 | 设计系统中央化成瓶颈；一致性压过真实场景；研究库积累但不改变决定 |

### 3.3 前端工程师

| 阶段 | 代表任务与证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 澄清页面/交互；复用组件；完成含 loading/empty/error/权限等局部状态；单元测试、人工走查、构建与回滚清单；查 console/网络错误 | 只实现截图；只测 happy path；构建成功即发布成功 |
| S1 入门/独立常规 | 核对旅程、API、浏览器、无障碍和性能约束；交付带测试与 telemetry 的纵向切片；组合组件、交互、视觉、无障碍、E2E 和负路径；用 RUM/客户端错误/trace 定位 | 覆盖率替代风险覆盖；错误被吞；客户端指标不分真实用户群 |
| S2 老手/复杂系统化 | 设计前端架构、性能预算和演进边界；建设共享库与发布护栏；治理测试分层/flake；推动框架或组件迁移，以用户侧 SLI 和组织开发效果验证 | 平台/框架先行；包体和性能预算脱离业务；迁移只有完成率没有收益 |

### 3.4 后端工程师

| 阶段 | 代表任务与证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 澄清字段/规则；按现有模式完成 handler 或任务；单测正常与明确错误；按脚本发布；用日志与关联 ID 定位；有回滚/求助点 | 错误一律 500；重试造重；正常路径通过就上线 |
| S1 入门/独立常规 | 建模领域、流量、安全和依赖；定义契约、幂等、并发、一致性、错误和 SLO；做契约/集成/负载/安全/恢复测试；处理 schema 兼容、灰度和回滚；用 SLI/trace/metrics/runbook 处置 | API 合同隐式；迁移不可回滚；日志多但无法关联用户影响 |
| S2 老手/复杂系统化 | 判断服务边界、建设/采购和系统风险；设计可演进版本、韧性和成本；建立框架/护栏、故障注入、低停机变更、错误预算与容量治理；用事故消除重复故障 | 微服务/平台成为目标；可靠性无限加码；技术债治理无现实指标 |

### 3.5 架构师

| 阶段 | 代表任务与证据 | 典型失败 |
|---|---|---|
| S0 新手/探路 | 整理功能与约束、画当前/目标组件关系、记录关键假设和依赖；检查发布依赖；更新 ADR；由资深复核高风险质量属性 | 图画得完整即“架构完成”；套面试模板；无量化场景 |
| S1 入门/独立常规 | 把性能、可靠性、安全、成本写成可测试场景；用 ADR 记录选项和权衡；提供 architecture runway/fitness checks；验证性能、韧性、安全、迁移和恢复 | 架构原则无验证；评审只查一致性；忽略组织和运营能力 |
| S2 老手/复杂系统化 | 对齐业务、技术、组织、监管与组合边界；建立演进架构、paved road、自治/例外治理和独立保证；从容量、事故、成本、拓扑漂移决定拆分、合并、简化或退役 | 架构委员会成审批瓶颈；标准压过情境；目标架构永不收敛到迁移结果 |

## 4. 跨职能工程对象

### 4.1 探索决定简报

```text
用户/问题｜证据与代表性｜竞争解释｜业务/技术/法规约束
no-build/继续门｜最危险假设｜决定者｜下一证据窗口
```

### 4.2 体验与服务合同

```text
旅程/状态｜内容｜响应式｜可访问性｜API/schema｜错误语义
性能/可靠性/安全等质量属性｜验收者｜版本/变更
```

### 4.3 增量追踪链

```text
结果假设 → 故事/验收 → UX 状态 → API/数据 → 代码变更
→ 测试 → telemetry → release flag → 现实结果
```

链上任何一段缺失都要显式暴露；不要求每个低风险变更使用重型工具，但必须能说明影响来自哪项改变。

### 4.4 发布合同

```text
版本/变更集｜风险与受影响群体｜提出/批准/执行/复核人
环境与数据迁移｜兼容策略｜灰度/flag｜回滚与恢复目标
观察窗口｜stop condition｜对内/对外沟通
```

### 4.5 运行反馈包

```text
产品结果｜用户分群｜SLI/SLO｜客服/研究｜事故｜安全/无障碍缺陷
成本｜错误预算/风险接受｜当时假设是否成立
```

### 4.6 迭代决定记录

```text
保持/扩大/改变/停止/退役｜当时证据｜竞争解释｜可逆性
责任人｜下次观察窗｜后续结果（追加，不改写当时未知）
```

观察窗、试点样本数和数值门槛必须由变更频率、历史基线、代表性、错误成本、判断目的与决定人共同校准。用户未给依据时只能列“待校准项 + 校准变量 + 确认人”，不得自创“接下来 N 次”“观察 N 天”或貌似精确的通过线。

## 5. 生命周期检查面

| 生命周期 | 必问判断 | 最小反馈门 |
|---|---|---|
| 机会/探索 | 真问题、目标用户、已有替代、最危险假设；为什么不是 no-build | 至少一种真实用户/业务证据能改变决定 |
| 范围/验收 | 结果、非目标、质量属性、边界状态、完成定义 | UX、工程、运营和决定者对关键合同可验证 |
| 设计/架构 | 旅程、状态、契约、威胁、故障、成本和迁移 | 原型/实验/技术 spike 证伪关键假设 |
| 实现/测试 | 纵向切片、错误、测试分层、遥测、权限 | 关键用户路径与负路径都有风险相称证据 |
| 发布/迁移 | 兼容、数据、授权、灰度、停止、回滚、沟通 | 观察窗口内能判断继续、暂停或回滚 |
| 运行/事故 | 用户侧结果、可靠性、安全、成本、分群与接管 | 异常可见、有人响应、决定与后续行动留痕 |
| 迭代/退役 | 假设是否成立；边际价值、债务、迁移与依赖 | 继续投入、改变或停止有明确证据和责任人 |

## 6. 高频边界场景

### 用户要的功能是否该做

把请求翻译成工作任务和结果，找现有替代与错误成本；获取最小多源证据；设置 no-build 与最小可逆实验。S0 给单一访谈/样例模板并复核；S1 检查代表性和行为数据；S2 做组合机会成本与停止机制。

### 设计系统组件是否可发布

依次验证有真实需要、可用/可访问、与现有模式一致、可跨场景复用、贡献与维护责任明确；自动检查、人工走查和用户/辅助技术验证互不替代。组件存在不证明整个服务可访问。

### 破坏性 API 变更

冻结“直接改”假设；定位消费者与版本；比较兼容扩展、版本化、迁移适配和同步切换；写弃用窗口、监控、回滚与责任人。架构师/后端提供技术证据，业务影响和剩余风险由有权者接受。

### 数据库迁移上线

检查前后向兼容、数据量/耗时、锁/容量、双写或回填、校验、回滚可能性、备份恢复、灰度和观察窗口。若回滚不可行，必须改变发布策略并升级批准，不用“测试通过”掩盖不可逆性。

### 线上事故后的迭代

先恢复与保护用户，再建立时间线和影响；区分触发、根因、放大条件和控制失效；行动项有 owner、截止、验证和删除无效控制的条件。复盘不做个人归罪，也不能以“加强意识”替代系统改变。

### 资深架构建议与团队现实冲突

把架构主张改写为质量属性场景和可证伪假设；列团队能力、迁移、运营、成本和组织边界；通过 spike/fitness check/事故或容量证据比较。头衔不能覆盖一手证据，局部妥协也要写触发重审条件。

矩阵组织材料只采用已证实的权责：`知会` 不得扩写成审核、护栏核对或批准。沟通语言、模板与收件人要求来自实际接收约定，不由“外企/HQ”标签推出；用户未要求外语版本时先交付其当前语言材料，必要时把翻译列为待确认选项。

## 7. 路由与验收

- 问题证据冲突 → `xb-analysis`；结果/范围/验收 → `xb-goal`；切片/依赖/发布门 → `xb-plan`。
- 实现和故障 → `xb-it`；产品指标、实验与 telemetry 语义 → `xb-data`。
- PRD、ADR、API、runbook、发布说明 → `xb-writing`；设计/代码/发布检查 → `xb-review`。
- build/no-build、go/no-go、keep/change/scale/stop → `xb-decision`。
- 角色权责和跨团队推进 → `xb-company`、`xb-stakeholder`、`xb-upward`、`xb-meeting`。

交付检查：

1. 是否识别了本轮角色、生命周期、决定 owner 与验收者？
2. 是否把用户结果、产品产物、技术交付和运行反馈分开？
3. 是否覆盖正常、错误、边界、迁移、观测和回滚，强度与风险相称？
4. 是否按阶段保留用户亲自判断和验证的部分？
5. 是否避免用岗位头衔、工具清单、代码量或上线次数证明能力？
6. 是否给出继续/改变/停止的现实反馈点，而非默认无限迭代？
