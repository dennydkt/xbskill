# 贡献与绩效证据核对

由 `../../xb-career/SKILL.md` 按条件加载；先读取同目录 `workplace-evidence-review.md`，共用其授权、材料定位与核对协议。缺文件时报精确路径并停止受影响核对。本文用于核查可取得的工作材料及评价依据；组织裁决、未开放的他人材料和现实评价变更均有独立权限边界。

## 先冻结核对对象

记录用户要确认的具体主张、任务/项目 ID、考核周期、争议交付版本、目标变化、截止日与可用材料范围。材料已经充分时直接核对；关键缺口只问当前最能改变动作的一项。每项判断挂原文件路径与行号、表格单元格、版本提交或记录 ID，同时保留原意、日期、来源人、事实/解释/未知类别。

至少保留两条会导向不同动作的解释：贡献记录遗漏与用户高估自身贡献；计分差错与按适用标准评分合理。先取得最能区分的任务分工、验收记录或规则条款，避免先写申诉再挑材料。

## 贡献核对

先核对争议表的用途与字段：发布负责人、文件作者、参与贡献和奖项署名可能是不同记录。表只写一人且用途未知时，结论限于“该字段目前记为此人，贡献登记用途待核”；即使已证实其他人的工作，也不能先判遗漏、抢功或提出确定更正。标题、首句和拟发草稿必须继承同一不确定性。只有记录明确要求列出该类贡献、实际贡献有证据且确实未记时，才判相应遗漏。

每个人分开标注“被分配的职责”“有证据的实际动作”“交付与验收结果”。承担验收样例职责、提出边界问题，只支持这些具体事实；缺少样例交付记录时不能写成完成验收准备。贡献草稿逐项回查来源，禁止用职责自动补齐完成状态。

逐项建表，禁止用文件数量、工时、提交次数或作者字段单独排列功劳：

| 必填项 | 核对动作 |
|---|---|
| 任务与承诺 | 对齐任务 ID、范围、预期结果、责任分工及变更授权；分开最初承诺与后来新增工作 |
| 版本与内容 | 比较交付所采用版本的具体增删和来源；列出复用、独立设计、修正、格式整理与被弃用工作 |
| 交付与验收 | 核对交付日期、接收方、验收条件与实际使用结果；草稿、发送、验收和采用分别标状态 |
| 协作贡献 | 逐人对应设计、实现、数据提供、验证、风险修复、协调及交接动作；保留依赖与他人补救记录 |
| 归属主张 | 把每条“谁完成什么”与证据/反证相连，给确认、部分支持、相反材料或待核实结论 |

文档作者或最后编辑者只能说明相关元数据，不能自动证明主要贡献。合并提交、代提交、模板复用及整理导出均可改变字段；回看内容变化、任务记录与实际验收。实际贡献与公司奖项/署名资格也需分开，后者按有权者适用规则核对。没有可用分摊规则时保留动作级贡献，禁止编造贡献百分比。

若贡献明确但记录遗漏，形成一条带坐标的更正建议及可直接使用的核对话术；若关键工作由同事完成，修正用户原主张，保留用户可证实部分；双方记录冲突时列冲突点与所需的有权复核者，不推断他人动机。

## 绩效核对

先确定规则的发布者、生效日期、适用岗位/周期、员工可见版本与变更记录。文件名“最新版”不足以决定适用版本；新旧规则冲突且无生效依据时只做各版本条件试算，不判定应得最终等级。

逐项输出 `评价项 → 适用条款/版本 → 权重 → 原始数据坐标 → 计算/裁量依据 → 原评分 → 核对结果 → 差额或争议 → 决定/复核人`。

- **可复算项**：核对分子、分母、周期、单位、封顶、扣分、缺失项处理、加权与舍入规则；展示实际代入、结果和差额。权重校验按规则明确的总量执行；缺少算法时列缺口，禁止补造。若可复算部分完整、裁量部分未决，只给确定部分及条件总分。
- **有裁量项**：核对等级锚点、原意评语、具体事件、发生日期、评价人及权限、证据范围和校准记录。主观判断有明确行为依据时保留；依据缺失标为待说明。跨人比较必须确认岗位、周期、规则和可比条件，禁止索取或猜测无权限的个人考核档案。
- **综合结论**：高销售额、交付数量或单一业绩只能支持对应评价项；质量、协作、合规及其他适用维度按其证据处理。算术正确、裁量依据充分、规则适用性、程序一致性分别给结论。材料支持评分合理或用户确有失误时如实写出，交付可执行的纠错/改进动作；仍可单列用户对规则的不同意见。

## 权限与评价链

逐项标记数据提供者、事实确认者、初评人、校准人、最终决定人、复核渠道和截止时间；未知保留未知。用户能够阅读自己的材料不自动取得他人绩效数据、公司外传或代发申诉权限。默认只在已授权范围内核对并形成草稿；外发、更改正式记录和提交复核按当前明确授权执行。权限不足时交付可由有权者核实的最小问题与坐标，禁止绕过访问控制。争议带来报复或隐私暴露风险时缩小材料与接收范围，把保护成本纳入用户选择。

## 正反例与翻转

- 正例：验收采用的版本含用户完成的规则设计和实现，同事仅做导出，登记表漏记用户。结论仅覆盖这些已核实动作，形成更正草稿；若后续版本证明主要实现来自同事，重新核对归属。
- 反例：用户为最后编辑者，任务与版本记录显示同事完成核心实现及修复。承认同事贡献，只保留用户可证实的整理/协调动作；若新增设计记录证明用户承担了关键方案，更新贡献表。
- 绩效反例：业绩分达到封顶，已生效规则还计质量和协作，具名事件与复核记录支持相关扣分。即使用户不满总分，仍报告计算及有据扣分结果；若扣分事件被证明不属于该周期、已撤回或规则适用错误，重新计算受影响项。
- 边界例：只有总等级与截断截图，没有规则版本、明细或原始记录。交付当前可确认事实与一份针对规则/明细的核对请求，暂停最终评分和动机判断。
- 登记用途边界：任务单写甲做设计、乙做验收样例、丙发布，记录表仅写丙；实际证据只证明乙提出问题。先查该表记录发布负责人还是参与贡献，保留甲的已证实设计和乙提出问题的事实，不将乙职责写成已交付样例，也不预判登记遗漏。

## 直接产物与现实回流

交付已填的贡献/绩效核对表、支持与不利证据、缺口、当前结论及一份最小核对草稿。草稿写清争议项、现有依据、希望核实的事实或具体更正；用户保留是否提交及接收人的决定。

每个未决项指定 `复核人 → 下一动作 → 截止日或下次校准事件 → 预期可观察材料 → 失败/翻转信号`。只完成草稿时声明“核对材料已完成，正式归属/评分变更待现实反馈”。收到有权者原意回复后回填 `原主张 → 新证据 → 保留/修正/撤回 → 是否更正记录/重算 → 用户收益与成本 → 下一反馈点`。逾期未回应、规则变更、材料冲突加剧或保护成本升高时调整核对路径；禁止把沉默当作承认错误。长期档案仍须用户明确授权。
