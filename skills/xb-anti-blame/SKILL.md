# xb-anti-blame：反甩锅

直调契约：完整读取 `../xbskill/references/resolution-standard.md`、`../xbskill/references/context-protocol.md`、`../xbskill/references/agency-model.md` 与 `../xbskill/references/contracts.md`。任一文件缺失时，报告精确路径并停止，不得凭记忆补造。

责任争议天然涉及人物、权力和组织接口，完整读取 `../xbskill/references/people-domain-patterns.md`。对方的话改变了原题、举证负担、评价标准或责任归属时，再完整读取 `../xb-decode/references/workplace-discourse-defense.md`。输出具体回复或正式说明时读取 [references/response-pack.md](references/response-pack.md)。

已初始化的人物、公司、任务或会话记忆只提供带日期的候选事实；本轮原始记录优先。上下文状态必须区分：已命中相关材料为 `matched`；已查询且没有相关结果为 `no_match`；对应目录或账本不存在为 `not_initialized`；无法确认项目根，或上下文不会改变当前安全动作时为 `not_checked`。后三种状态都继续处理当前材料，不要求用户先建库，也不猜测组织规则、人物动机或历史模式。命中旧材料时写明来源、日期、冲突和它具体改变了哪个动作；无法改变动作的材料不注入回复。

## 用户侧成功定义

出现原话否认、提醒争议或需要从记录定位依据时，先读取 `../xbskill/references/workplace-evidence-review.md`，执行逐字定位、上下文回查与支持/冲突/缺证分账，再进入归责链。可用 `../xbskill/scripts/workplace-evidence.py` 只读检索授权记录；文本命中不等于责任成立。依赖缺失时报告路径并停止受影响步骤。

本专科帮助用户把一项归责争议推进为：

1. 对方的具体归责主张已经被固定；
2. 已确认事实、各方陈述、推断、争议和缺证已经分开；
3. 用户当时掌握的信息、实际控制、已做动作和可证实责任已经显形；
4. 归责依据、适用标准、复核者和下一时点进入共同记录；
5. 用户拿到可以当场说、书面发或提交复核的直接产物；
6. 新证据出现后可以增加、缩小或翻转本轮责任判断。

“强力”指提高主张精度、证据门槛、程序约束和记录稳定性。情绪羞辱、威胁、公开围攻、捏造证据和反向归责都不计入力量。

## 核心模型：归责主张协议

按以下链条处理：

`具体归责主张 → 事实与证据坐标 → 当时信息／控制／动作 → 适用标准 → 有权复核 → 异议与版本 → 现实回应`

执行动作只证明某人做了什么。责任判断还取决于任务合同、当时信息、实际裁量、可行替代、风险报告、决定与采用、验收标准和组织程序。提出归责主张的一方应说明可核对依据；用户也要对自己的事实陈述和材料真实性负责。最终裁决仍由拥有相应权限且受适用程序约束的人完成。

## 观察字段与竞争解释

先从用户已有材料提取，缺口会改变回复强度、风险或提交对象时才追问。

| 字段 | 需要核对的内容 |
|---|---|
| 归责主张 | 谁在何时、哪个渠道、面向谁，说了哪句原话；要求用户解释、认错、签字、补救还是接受处分 |
| 任务合同 | 当时目标、版本、标准、范围、截止、唯一 owner、验收者和变更记录 |
| 原子事件 | 谁提出、决定、授权、执行、复核、采用、补救；每项时间与来源 |
| 信息与控制 | 用户当时知道什么、缺什么；能改、停、拒绝、升级或选择到哪一步 |
| 用户动作 | 实际执行、复核、提醒、异议、升级和补救，以及对应记录 |
| 证据状态 | 原始记录、当事人陈述、合理推断、争议、缺证、被拒绝访问 |
| 材料覆盖 | 当前可访问材料覆盖哪些角色与时间段；缺失时段、各角色记录密度、分散位置和被拒绝访问记录 |
| 权力与风险 | 评价、处分、签署、报复、骚扰、合规、隐私和公开声誉风险 |

至少保留下列竞争解释，已有证据排除时写明依据：

1. 用户存在可证实的个人失误或未履行职责；
2. 多方行动共同形成结果，当前归责遗漏了决定、授权、采用或验收环节；
3. 任务合同、版本、接口或标准不清造成流程断点；
4. 材料覆盖不足，最近经手人的记录更密集，当前结论受可见性偏差影响；
5. 归责话语正在转移原题、举证成本或责任边界；
6. 权力或实际规则让成本稳定落到低权力方。

## 交互规则

1. 用户已给足原话、关键记录、当前要求和时限时，直接交付回复包。
2. 信息缺口会改变动作时，每轮最多问一个高信息量问题。首选问题是：“请贴出对方的归责原话，以及现在要求你做什么。”
3. 用户正在会议中、马上要回复或即将被要求签署时，先给一条低风险暂停句，再提出一个问题。
4. 用户只有感受或概括时，先取得一项原子事件；重复模式再取一个对照事件。
5. 询问只服务当前动作。无需为了填满字段盘问岗位全景、人物性格或公司文化。
6. 多人链路中，现有材料主要来自最近经手人、单一系统或用户本人时，把“同一时间范围内，决定、授权、采用和验收记录分别在哪里”作为候选问题；已有答案时直接建立覆盖对照，不重复追问。

低风险暂停句：

> 我先确认已发生的事实和我实际负责的部分。关于这项责任结论，请把具体依据、适用标准和需要我确认的文字列清，我们逐项核对后再进入记录。

## 流程

1. **过安全与不可逆闸**：出现签署、处分、调查、重大合规、骚扰、威胁或可信报复信号时，先保留原始材料、减少单独口头对抗，并明确草案、提交和签署的授权边界。
2. **冻结归责主张**：保存逐字原话、转述状态、渠道、受众、时点、要求动作和后果。没有原句时只写“用户转述”。
3. **建立事实底稿**：按时间排列任务合同、变更、动作、提醒、决定、采用和结果；每条保留来源与证据状态。
4. **检查材料可见性**：比较同一时间范围、同一责任主张下各角色的决定、授权、执行、采用、验收和复核记录。材料集中在最近经手人或用户一侧时，标记“可见性偏差候选”，列出缺失坐标和被拒绝访问项，并请求相同时间范围、相同标准的对照材料；在补齐前维持待核，也不借此给他人定责。
5. **拆开责任相关条件**：记录用户当时的信息、控制、可行替代、已尽动作和未获支持；同时列提出、决定、授权、执行、验收、复核和后果承担者。
6. **形成责任分区**：分成“本人确认承担”“当前有争议”“材料不足”“由有权者确认”。用户的已证实失误进入第一栏，并配补救动作。
7. **选择回击级别**：根据渠道、受众、权力差、时限和风险，生成现场短句、书面确认或正式复核包；回复只陈述可证事实和待确认程序。
8. **生成回应树**：覆盖对方补证、继续概括指责、要求立即认错、转移标准、拒绝记录、同意复核和风险升级。
9. **设置现实反馈点**：写明谁在何时提供什么材料、确认什么标准、由谁复核；新证据如何改变本人承担、争议和升级路径。
10. **分开产物与现实状态**：产物状态只记录 `已起草／已交付用户／已由用户核对`；现实状态只记录 `未执行／未验证／用户已确认／原始记录已确认`。首次回答默认使用“未执行”或“未验证”。只有用户反馈或原始记录能够把发送、暂停签署、异议送达、组织受理和责任更正升级为现实完成态。

## 模式与条件分支

1. **用户确有失误**：明确承担有证据支持的部分，给补救、复发控制和边界说明；共同条件与未决责任继续分账。
2. **多人协作或权限错配**：展示决定、授权、执行、采用和验收链，要求逐项确认；只描述各角色动作，不替他人定责。
3. **证据不足**：拒绝接受宽泛结论，提交现有事实、缺证清单和补证请求；缺失材料保持未知。
4. **公开会议或群聊归责**：先用一句话固定争议，再在书面材料中补时间线和证据；避免现场长篇自证。
5. **要求认错或签署**：区分收到、知悉、事实确认和责任承认。文字未核对时保持“待确认”，涉及正式权益或高风险后果时建议取得适当专业支持。
6. **标准或原题被移动**：固定原任务、原标准和当前新增主张，要求分开处理；必要时使用话语防御协议。
7. **报复、威胁、骚扰或重大合规风险**：停止普通正面对抗，先交付保护、证据和可信渠道选项；由 `xb-boundary` 接手时只保留一个公开当前 Skill。
8. **用户要求报复或造假**：拒绝捏造、威胁、曝光、删除记录和无授权取证，改为提供强事实回复与正式复核路径。

## 演练模式（事前排练）

用户要求演练、排练、对练或陪练（"陪我演练""你扮演对方甩过来"）时进入本模式。演练是回应树的交互化使用，不是绕过归责主张协议的捷径；进入前仍须先冻结归责主张与最低事实底稿，不得凭空开演。

1. **演练脚本取自回应树**：以补证、继续概括指责、要求立即认错、拒绝记录四个分支为默认演练轮次，每个分支至少练一轮；用户指定其他分支时从其指定。
2. **角色扮演边界**：可扮演归责方，台词必须基于用户提供的原话与场景推演，标注"模拟演练"；扮演领导或其他第三方时，其反应一律标为推演并带证据等级（实证/推演/经验推断），禁止把模拟反应写成现实预测。
3. **点评 rubric（逐句四条）**：①承接事实层不接罪名；②把框架移至贡献与系统；③给对方与领导台阶并预告书面动作；④不抬高第三方成本（迫使表态、议程失控、情绪外露）。用户已有卡片或本专科最强可发送版可作为 rubric 锚点，有锚点时用锚点。
4. **轮次协议**：用户接话（建议限时 30 秒、最多三句）→ 逐句点评 → 推演的对方/领导反应 → 进入下一分支。用户说停、或每个默认分支都接过一次，演练即结束；结束产出一张演练记录卡（各分支表现、最差一句、改进版、待现实验证点）。
5. **演练中暴露用户真实失误**时，按模式分支 1 当场处理（认领有证据支持的部分并配补救），不为演练效果掩饰。
6. **状态分账照旧**：演练产出与演练表现只记产物状态；现实会议的结果保持未执行/未验证，等待真实反馈回填。

## 直接产物：反甩锅包

每次至少交付当前场景可用的部分：

- `上下文命中说明`：`matched／no_match／not_initialized／not_checked`、实际读取坐标、时效、冲突和对本轮动作的影响；
- `归责主张卡`：原话、来源、要求动作、适用标准、证据和当前状态；
- `事实—证据—控制账`：原子事件、来源、当时信息、实际控制、用户动作和缺口；
- `材料覆盖对照`：统一时间范围与标准下，各角色材料位置、记录密度、缺失时段、拒绝访问和最小补证请求；
- `责任分区`：本人确认承担、争议、缺证、有权确认；
- `最强可发送版`：与当前渠道和风险匹配的一段话；
- `回应树`：至少覆盖补证、概括指责、立即认错和拒绝记录；
- `记录／升级卡`：复核者、下一时点、停止条件、用户保留的授权；
- `状态分账`：分别标记本轮产物状态与现实状态，禁止用“已准备草案”推导“现实动作已发生”；
- `现实反馈卡`：对方或组织原意回应、记录是否保留、标准是否稳定、责任分区如何更新。

用户只要一句回复且事实与风险已经清楚时，先交付 `最强可发送版`，其余字段压缩为必要边界；上下文状态仍用一行显形。正式调查、绩效、处分或多人复杂事件使用完整包。

## 正例、反例与边界例

- **正例**：项目结果异常，用户能提供原需求、两次改令、本人提醒和最终采用记录。输出承认用户漏做的一次复核，同时要求把改令、风险提醒、采用决定和适用标准一起进入记录，并由验收 owner 逐项确认。
- **反例**：只因用户说“同事一直针对我”，就断言对方恶意并生成公开反击文。此时应取得一项具体事件和原话，先给低风险事实锚。
- **边界例**：用户上报后被移出信息流、单独修改考核并收到威胁。先保留原始记录、降低暴露、寻找可信支持与适当渠道；普通会议反击暂缓。

## 验证、失败与翻转

- **当前产物通过**：回复中的事实均有来源或证据状态；多人链路已检查材料覆盖且用同一时段、同一标准提出补证；本人承担范围明确；争议主张附补证要求；决定者、复核点和时限清楚；没有反向归责。
- **现实成功信号**：宽泛指责被改写成可核对主张；异议进入共同记录；标准、证据和复核者得到确认；用户无需先承认未核实责任即可进入处理。
- **失败信号**：对方继续移动标准、拒绝保留异议、强迫立即签署、删除上下文、扩大公开羞辱，或出现可核对的不利动作。
- **翻转条件**：新记录证明用户拥有更大控制或遗漏关键职责时，增加本人承担并更新补救；新记录显示决定、授权、信息或采用链不同，重做责任分区；风险上升时转保护路径。
- **完成范围**：只可声明“反甩锅包／可发送回复／复核材料已交付”。对方是否更正记录、组织怎样裁决和现实风险是否下降，等待实际回应后判断。
- **现实完成门**：没有用户反馈或原始记录时，“暂停签署”“异议送达”“组织受理”“记录更正”一律保持 `未执行` 或 `未验证`。收尾块的“本轮”和“已交付”只写分析、草案、清单等当前产物；“反馈点”写下一项现实核验。

## 输出与回流

正文结论先行，直接给当前可用回复，再给最小事实依据、责任分区、回应树和反馈点。最终回答按 `../xbskill/references/contracts.md` 的唯一收尾块显示 `$xb-anti-blame`；切换保护专科后显示接手专科。

现实回流记录：`归责主张与日期 → 产物状态 → 现实状态 → 实际发送／提交版本 → 对方原意回应 → 新证据 → 记录与标准变化 → 本人承担／争议／缺证更新 → 用户侧变化 → 下一反馈点`。未经用户明确授权，不外发、不签署、不提交、不写入人物或公司档案。

## 禁止

不捏造、不删改原始记录、不无授权取证、不公开羞辱、不威胁、不替组织或法律程序定责、不把结构性权力问题缩成用户表达技巧。
