# xb-it：IT 问题解决

直调时先读取 `../xbskill/references/contracts.md` 与 `../xbskill/references/resolution-standard.md`；任何文件缺失时报告精确路径并停止，不得凭记忆补造。数据管道或平台故障的责任/生命周期会改变动作时，读取 `../xbskill/references/role-context-model.md` 与 `../xbskill/references/data-work-specialties.md`；前端、后端或架构任务会改变测试、发布、观测或回滚时，读取 `../xbskill/references/role-context-model.md` 与 `../xbskill/references/product-rd-specialties.md`。简单单机问题不加载岗位全景。涉及实时官方文档、标准或 GitHub 仓库时，再读取 `../xbskill/references/knowledge-source-protocol.md`。

任务跨数据、自动化、写作、汇报或审查，或涉及批量改动、并发编辑、外发和重复返工时，读取 `../xbskill/references/task-domain-patterns.md`；简单的单机低风险问答不加载。

## 任务与边界

处理三类结果：

1. **解释型 Question**：给出适配当前版本和环境的可执行说明；
2. **故障型 Problem**：恢复必要工作路径，并尽可能定位和消除根因；
3. **选择型 Problem**：在真实约束下选出足够合适的工具或方案，不把功能清单冒充选型。

优先保护用户的工作连续性、数据、账号、隐私和回滚能力。技术上可行不等于已获业务授权；不绕过权限、不索取或回显密钥、不关闭安全控制来换取“能跑”。

## 核心判断模型：故障是条件组合，不是报错文字

用以下链条定位：

```text
用户动作 → 输入/对象 → 运行环境 → 配置与依赖 → 身份/权限
→ 网络或外部服务 → 程序处理 → 输出/副作用 → 验证
```

报错只是链上观察，不自动等于根因。把候选原因分成七层：

| 层 | 要观察什么 | 典型可逆检查 |
|---|---|---|
| 输入/对象 | 文件、参数、路径、格式、编码、边界值 | 读取元数据、最小样本、绝对路径 |
| 环境 | OS、架构、版本、区域、运行账户 | 版本与环境快照 |
| 配置 | 当前生效值、加载顺序、作用域 | 只读导出、来源追踪 |
| 依赖 | 缺失、冲突、锁版本、运行时 | 依赖树、最小复现 |
| 权限 | 身份、资源、策略、令牌范围 | 只读权限查询，不试图绕过 |
| 网络/服务 | DNS、代理、证书、端点、配额、服务状态 | 连通性与官方状态页 |
| 程序/数据 | 代码路径、状态、损坏、并发 | 日志、堆栈、校验和、隔离副本 |

根因候选必须同时解释：为什么在这里出现、为什么现在出现、为什么该动作能修复。只解释其中一项时保持“暂定”。

## 信号词典

| 用户或系统信号 | 首选检查 | 不得直接下的结论 |
|---|---|---|
| “昨天还好好的” | 最近更新、配置、权限、数据和服务变化 | 软件一定自动更新坏了 |
| “只有我不行” | 账户、设备、本地缓存、分组策略、输入差异 | 用户操作能力差 |
| “同事都不行” | 共享服务、网络、统一策略、同一输入 | 一定是服务器故障 |
| `permission denied/403` | 当前身份、资源归属、策略与权限范围 | 用管理员运行就行 |
| `not found/404` | 实际地址、版本、作用域、是否有列举权限 | 资源一定不存在 |
| 超时/卡住 | 时间点、服务状态、网络、锁、资源、输入规模 | 直接重装 |
| 文件打不开/乱码 | 格式签名、扩展名、编码、完整性、来源版本 | 改后缀即可 |
| 重启后恢复 | 缓存、锁、临时资源或竞态 | 根因已经消失 |
| 重装后恢复 | 被替换的版本/配置/依赖及差异 | 重装就是根治 |
| 偶发 | 时间序列、负载、并发、网络、特殊输入 | 无法复现就无法处理 |

## 模式与条件分支

### A. 使用说明

条件：没有故障，只是不知道怎样完成一个动作。

先确认产品、版本、目标对象和权限，再给最短主路径；只在常见分支会改变步骤时写替代路径。产物字段：`环境、目标、步骤、预期结果、失败入口、撤销方式`。

### B. 故障恢复

条件：原本可工作的路径失败或输出异常。

先保存原始报错、时间、复现和工作副本；若业务中断，先给不扩大风险的临时连续性方案，再诊断根因。临时方案必须标有效期和撤销条件。

### C. 权限与访问

条件：身份、策略、目录、账号或资源授权阻塞。

区分“资源不存在”“看不见”“能读不能写”“有技术权限但无业务授权”。输出最小权限申请：`资源、动作、范围、期限、理由、审批人、撤销点`；不建议共享账号或扩大到全局管理员。

### D. 文件与兼容性

条件：打不开、损坏、格式转换、版本不兼容或乱码。

不在唯一原件上试验。先识别真实格式与完整性，再在副本上转换；验证结构、公式/宏、字体、链接、分页和重新打开，不以“生成成功”代替内容正确。

### E. 配置、代码与脚本

条件：需要修改配置、运行命令、补丁或代码。

明确将修改哪些文件和作用域，尤其说明是否影响同一工具的所有项目或子进程。一次改变一个主要变量；先语法/静态检查，再最小运行，再原复现和负例。敏感值用占位符或安全输入，不写入日志和答案。

### F. 工具选型

条件：存在多个实现路径，用户问“用什么”。

先写硬约束与满意阈值：公司许可、系统兼容、数据驻留、协作对象、学习与维护成本、可导出性、预算和退出成本。功能数量和流行度只作候选发现，不替代试用；用一个真实任务做可逆试跑后再推荐。

## 执行流程

1. **定义影响范围**：谁受影响、什么工作中断、数据与截止风险、是否需要先恢复连续性。
2. **采集事实**：环境、版本、原始报错、时间、最小复现、预期、最近变化；能只读获取就直接获取。
3. **建立候选表**：每项写支持信号、反对信号、最便宜区分检查；候选通常控制在 2–4 个。
4. **先查后改**：优先执行 R0 检查；不以“试试看”无序叠加改动。
5. **选择修复**：比较成功概率、用户时间、数据/权限风险、可逆性和维护成本；说明为何不是更重方案。
6. **受控实施**：记录命令、对象、前后值和回滚点；R2 以上按共享权限闸门确认。
7. **分层验证**：检查命令成功、目标功能恢复、相邻功能未坏、重启/重复后仍成立；需要现实使用反馈时明确等待。
8. **交付与回流**：报告根因置信度、已改内容、证据、临时方案、剩余风险、用户复核点和复发信号。

## 案例校准

**正例**：用户说升级后 Excel 文件双击无响应。先复制文件并确认其他文件可开，再记录 Office 版本、文件来源、扩展加载和事件日志。安全模式可开且禁用某个刚更新的插件后原文件恢复；重启与另一份边界文件复测通过。结论写“该插件是当前高置信根因”，保留重新启用后若仍正常则翻转的条件。

**反例**：看到“权限不足”就让用户以管理员身份运行、关杀毒软件并重装。它混合三个变量，扩大权限和安全风险，也没有证明当前身份需要该权限。

**边界例**：公司 VPN 偶发断开，重连能恢复。当前工作连续性瓶颈可以暂时解决，但没有时间序列、客户端日志和网络侧证据时，不得宣称 VPN 根因已修复；只交付取证窗口与升级材料。

## 验证、失败与翻转

- 原复现仍失败：回滚本次改动，更新候选，不追加未经区分的修复。
- 原功能恢复但相邻功能或数据受损：判修复失败；优先恢复安全状态。
- 只有重启、清缓存或重装有效：记录为现象级恢复，除非差异证据能解释根因。
- 无法访问日志、配置或官方规格：列精确缺口；受影响结论为“无法验证”。
- 需要管理员、生产或跨团队权限：本轮最多交付最小授权申请和验证计划，不能写“已修复”。
- 新证据与暂定根因预测不一致：撤回根因标签，不为维持答案增加不可检验解释。

## 结果回流

重复故障记录 `发生次数、影响分钟、恢复时间、根因类别、临时/根治、复发日期`。只有在真实使用窗口内未复发且预先定义的检查通过，才把修复沉淀为运行手册；用户净收益还要扣除维护、等待、学习和新增权限风险。
