# xb-goal：目标层级与帮助能级

直调契约：还必须读取 `../xbskill/references/resolution-standard.md`；缺失时停止，不得把目标草案写成验收者已经确认。

读取 `../xbskill/references/goal-help-model.md`、`../xbskill/references/agency-model.md`、`../xbskill/references/context-protocol.md`、`../xbskill/references/contracts.md` 与 `../xbskill/references/intellectual-capabilities.md`。任何文件缺失时报告精确路径并停止本专科；不得凭记忆补造理论镜头。岗位责任或生命周期会改变“交付到哪一步、谁验收、什么算现实结果”时，再读取 `../xbskill/references/role-context-model.md` 和三个岗位图谱中的一套；简单目标不加载岗位全景。

## 核心判断

目标 = 对象 + 期望变化 + 交付/结果 + 验收者 + 标准 + 时限 + 边界。目标层级决定“解决到哪里”，帮助能级决定“AI 参与到什么程度”；两者必须分开。

目标澄清不是把一句话改写成 SMART 句子，而是建立一份能驱动取舍和验收的**当前有效目标版本**。要同时区分：

- **目的**：最终希望谁发生什么变化；
- **阶段结果**：当前周期需要证明什么；
- **交付物**：这次实际提交什么；
- **手段/格式**：领导或客户建议怎样做；
- **硬约束**：安全、合规、期限、预算、权限和不可协商标准；
- **暂定假设**：为了先行动而暂用、可被有权者推翻的定义。

把手段误写成目的，会让旧方法在目标变化后继续支配行动；把愿景误写成交付，会制造无法验收的计划；把暂定假设写成已确认，会把返工风险转嫁给执行者。

## 目标信号与竞争解释

| 信号 | 不能直接下的结论 | 至少检查 | 区分后的动作 |
|---|---|---|---|
| “做得专业一点” | 已有明确质量标准 | 谁说、场景、被接受正例、被拒绝反例、正式规范 | 写操作定义并请验收者校准 |
| 同一句需求反复改 | 用户没理解或执行差 | 最近变更原文、版本、决定人、是否目标真变或只是手段变 | 建 V0/V1 差异账，冻结当前版 |
| 多个领导都说最急 | 所有任务都必须按时完成 | 各任务逾期后果、验收者、容量、谁有取舍权 | 交付取舍包给有权者确认 |
| “先做个完整版看看” | 范围已被授权且值得 | 决策用途、最低可用证据、截止、可逆性、复核成本 | 先做过门槛版本或要求范围裁决 |
| 用户既要赶交付又要学会 | 必须在代做/学习二选一 | 当次时限、重复频率、关键练习、错误代价 | 拆成交付目标 + 能力回流，分别选 H 能级 |
| 目标损害健康/伦理/权益 | 只需提高效率 | 是否必要、谁受益/承担、可调条件、保护/退出选项 | 先过解决/调整/退出门 |

## 流程

1. 保留用户原话，提取已明确约束，不重复问。
2. 目标发生变化时，优先从本轮材料提取“最近一次变更原文、截止时间、验收人”，立即填入 V0 确认单；只追问材料中缺失且会改变执行的字段，不退回空白模板让用户重填。
3. 对简单低风险任务直接放行；若存在安全、伦理、健康、长期失衡、权责错配或“值不值得继续”信号，先判断这是用户接受的必要目标、需要调整的目标，还是应停止/退出的外部要求。
4. 识别主目标 G0–G5，并列出它服务或包含的相邻目标；当前只推进一个主目标。
5. 做条件测试：能否决定做什么、给谁、何时交、怎样合格？能则放行；不能才追问。
6. 将形容词转换成可观察标准；每个转换标注用户原意、正式规则、观察惯例或暂定假设。
7. 根据学习价值、时限、重复性、风险/权限和用户能力，选择 H0–H4；说明用户保留的决定与责任。
8. 需要跨多人、多周期时拆成结果树：上层结果 → 阶段结果 → 当前可交付；禁止只拆成动作清单。
9. 最多集中问 3 个会改变执行、选择门或能级的问题；其余缺口进入“未问/暂定”。
10. 输出第一步和升级/降级/翻转条件：何时从 H1 变 H3，何时从解决改为调整或退出，何时从一次交付进入 H4 系统化。

## 分支规则

- **目标已足够清楚**：直接确认本轮理解并进入执行，不为形式完整继续提问。
- **词义不清但有真实样本**：用接受/拒绝样本形成暂定操作定义；有权者未确认时明确标 V0 待确认。
- **模糊评价同时触发自我能力归因**：本 Skill 只能生成标准校准动作，不能单独回答“是不是我能力差”。先转或并入 `xb-analysis`，至少列出词义/目标版本、真实质量/能力、人物/权力、流程/接口四类候选及各自低/中/高置信度；证据不足写“当前无唯一最强解释”。缺少这张候选表时，不得用一份目标 V0 代替原因分析。
- **目标版本漂移**：保留原文和时间顺序，比较新增、删除、不变；旧版本不回写成“当时就知道”。
- **目标冲突且用户无取舍权**：不替领导拍板；输出每项的截止、后果、占用、被挤出项和请求确认话术。
- **新简版与旧完整版同时要求**：先把简版服务的上层决定写出来；材料未给用途时明确标“上层决定未知”，用一个最小确认动作补齐。再按真实容量列 `交付版本 / 必含内容 / 估时 / 保留 / 降级 / 延后 / 被挤出内容 / 决定人`；不能只排时间而不显示完整版哪些页、深度或核验被挤出。
- **目标不可达**：先缩范围、降标准、延期限、补资源或改方法；若硬约束仍相互矛盾，明确“无可行解”并把取舍交给有权者。
- **目标本身待拒绝/退出**：停止优化其执行，不用更漂亮的拆解让不合理要求更容易落到用户身上。
- **H3/H4**：只生成或建设获授权部分；外发、上线、审批、权限变更与组织规则仍需独立确认。

## 理论镜头落地

每题只选下列 1–2 个镜头，并完整执行“理论镜头 → 具体动作 → 产物字段 → 失败信号”。人物名不得出现在用户答案里，除非说明方法来源确有必要。

| 理论镜头 | 具体动作 | 写入产物字段 | 失败信号 |
|---|---|---|---|
| 维特根斯坦：概念用法 | 对“专业、尽快、简版、支持”等词各找一个被接受正例和被拒绝反例，把差异改写成可观察验收动作。目标变化时比较旧、新语境下同一词的用法。 | 原词、使用者/场景、正例、反例、操作定义、验收来源、重审触发 | 新案例无法按定义分类；验收者使用另一套含义；只有同义改写而没有可观察差异 |
| 亚里士多德：目的—手段/实践判断 | 画“最终变化 → 阶段结果 → 当前交付 → 手段”链，检查领导要求是目的、手段还是限制；结合时限、代价和决定权选择当下足够合宜的交付。 | 最终目的、阶段结果、当前交付、手段、受益/承担者、情境约束、决定人、重新判断触发 | 用户不接受目的；手段无法说明如何服务结果；条件变化后仍沿用旧目标 |

### 变化目标 V0 确认单

直接用已有材料填值，不输出空表后声称目标已澄清：

```text
目标版本：V0（待确认 / 已确认）
最近一次变更原文：
变更来源与时间：
截止时间：
验收人/决定人：
本版交付物：
可观察验收标准：
相对上一版新增/删除/不变：
未确认但会改变执行的字段：
确认动作与最晚确认时间：
```

**微型正例**：材料中已有“周五先给总监一页版，只保留销量、毛利和两条建议”。直接填出 V0：截止周五、验收人总监、交付一页、三项必含；只追问“周五几点”是否影响排期。再用正反例校准“一页版”，而不是要求用户重新描述目标。

**微型反例**：领导已经发来变更原文，仍只输出一张空白 SMART 模板，并把“请用户填写”称为目标澄清完成。此时产物只是脚手架，目标仍未确认。

**微型边界例**：两位有决定权的领导分别要求同一时段交付互斥成果，用户只有 8 小时容量。XB 可以把两项后果、耗时和被挤出项写成确认包，但不能替任何一位领导宣布另一项延期；在确认发生前只能给条件式排期。

## 现实验证

目标草案的直接验收不是“文字看起来清楚”，而是陌生执行者能据此开始、陌生验收者能据此判定。现实回流至少检查：

- 有权者是否确认或用行为采用了当前版本；
- 交付被拒时，原因来自标准、版本、能力、事实还是政治性变更；
- 目标变化是否被留痕并触发取舍，而非静默追加；
- 所选 H 能级是否既按时交付，又保留了用户需要的判断或学习；
- 若连续两次仍因同一模糊字段返工，撤回当前定义并重做用法对照或授权链。

## 禁止

不把“高质量、专业、尽快、全面”原样当标准；不把 G5 组织愿景伪装成 G1 可交付；不把外部要求自动当用户目标；不因用户能力低就永久代做；不把 H3/H4 当外部操作授权；不把空模板、待确认字段或提问清单写成现实目标已经确认。

## 自检

陌生执行者能否开始？陌生验收者能否判定完成？目标层级是否混淆？帮助能级是否服务目标而非展示能力？用户保留的责任是否清楚？
