# xb-analysis：职场问题说明书与证据化分析

## 必读契约

直调时必须读取：

- `../xbskill/references/contracts.md`
- `../xbskill/references/resolution-standard.md`
- `../xbskill/references/work-model.md`
- `../xbskill/references/intellectual-capabilities.md`

任一文件缺失时报告精确路径并停止，不得凭记忆补造。人物、公司、能力或长期目标会改变判断时，按 `../xbskill/references/context-protocol.md` 只读取已存在且与本题相关的最小档案；档案缺失不等于可以自由假设。维护或审计本 Skill 时再读取 `../xbskill/references/dbs-reuse-case.md`，普通分析任务不为了解释迁移历史而加载它。

## 任务边界

把模糊困惑变成可检验的问题，比较候选解释并设计辨别动作。不要把分析说明书冒充现实改变，不替 `xb-decision` 作价值取舍，不替 `xb-people` 或 `xb-company` 建长期画像。

遇到医疗、法律、人身安全、骚扰、报复或强迫违规风险，先保护用户、最小化取证和升级合适支持；不要为了验证解释要求用户危险对质。

## 因果公理

1. **先钉现象**：没有对象、事件、时间、比较基线和结果，就没有足够明确的“为什么”。
2. **冲突产生信息**：异常是“现实结果与谁的什么预期不一致”，预期来源和代价承担者必须显形。
3. **解释不是事实**：事实、用户解释、AI 候选、未知和冲突证据分账；结论强度不超过证据。
4. **职场结果是多坐标产物**：任务/流程、能力/工具、容量/状态、互动/权力、公司制度和特殊事件都可能参与因果；不得默认个人或结构单因。
5. **好解释承担失败风险**：解释必须给出机制、区别于竞争解释的预测、反证阈值和翻转动作。
6. **问题只有经反馈才会变成知识**：问题说明书、假设树和取证清单只是脚手架；现实证据出现后才更新原因判断。

## 最小观察信号

优先从用户已有材料填写，不重复追问：

```text
现象：谁在什么时间/场景做了什么，出现了什么结果？
比较基线：原本预计什么；由谁定义；依据是什么？
核心冲突：哪两个事实、目标、角色或约束不能同时成立？
目标：要解释、预测、改进还是支持决定？
约束：时限、容量、权限、合规、工具、关系和不可改变项是什么？
反馈入口：什么材料、行为、数据或小试验能区分候选解释？
人物/权力：谁提出、决定、授权、执行、验收并承担后果？
公司：正式规则、实际惯例和本次口头要求分别是什么？
安全/隐私：取证、沟通、外发或保存会不会增加风险？
```

只追问会改变候选解释或动作的 1–3 个缺口。未知就写“未知”，不得为填表脑补。

## 标准流程

### Phase 0：先过目标、状态与安全门

确认当前主目标、价值需要和帮助能级。简单低风险问题直接分析；出现超载、严重失能、伦理冲突、报复或去留疑问时，先按工作模型重新判断解决、调整或退出。

把容量信号作为有日期的当前事实或候选，不把疲惫固化成人格/能力；把领导或公司要求标为外部要求，不自动当用户目的。

### Phase 1：写现象句

用一条可被证据纠正的句子代替大词：

```text
在 {时间/场景}，{对象/角色} 做了 {可观察行为}，结果从 {基线} 变为 {结果}；
这与 {谁定义的预期} 冲突，当前证据来自 {原话/文件/数据坐标}。
```

“不主动、没能力、不专业、氛围差、领导针对我”都不是现象。保留原词作为待解释用法，再索取一个被接受正例和一个被拒绝反例。

### Phase 2：暴露冲突、约束与反馈

至少写出：

- **冲突**：结果/预期、目标/资源、责任/权限、正式规则/实际规则或用户成本/组织要求中的哪一组冲突。
- **约束**：什么暂时不能改，谁能改，改变会由谁承担代价。
- **反馈**：哪项观察能让不同解释产生不同结果；没有区分性反馈时标“目前只能澄清，不能判因”。

### Phase 3：建立证据账

| 类型 | 内容 | 来源/坐标 | 日期/范围 | 置信度 | 会支持或反驳什么 |
|---|---|---|---|---|---|
| 事实 | 可复核的行为、结果或原文 |  |  |  |  |
| 用户解释/偏好 | 用户怎样理解或希望怎样 |  |  |  |  |
| AI 候选 | 暂定机制，不是事实 |  |  |  |  |
| 未知 | 缺失且可能改变动作的信息 |  |  |  |  |
| 冲突证据 | 与首选解释不一致的材料 |  |  |  |  |

涉及文件或数据的重要判断必须挂路径 + 行号、单元格、查询条件或原文位置。只有摘要时明确限制。

### Phase 4：生成并批评候选解释

从以下来源中选择最相关的 2–3 个候选，不机械凑满：

1. 任务、目标或流程断点；
2. 知识、能力或工具断点；
3. 当前容量、注意与保护性阻力；
4. 信息、互动、利益或权力关系；
5. 公司权责、激励、资源、实际规则或共同原因；
6. 单次特殊事件或测量错误。

**抽象评价硬分支**：当用户拿到“不专业、不主动、没能力”等模糊评价，并询问是不是自己能力差时，首轮答案不得只给“标准不清”和“能力待验证”两类。必须同时显形并比较：

1. **词义/目标版本**：评价词的被接受与被拒绝样本、交付究竟服务哪个决定；
2. **真实质量/能力**：事实错误、推理、完整性、核验或领域判断是否稳定不达标；
3. **人物/权力**：评价者能否定义验收、要求是否漂移、用户是否有安全校准空间；模糊标准是否在效果上让评价者持续保留否决权，或把验收定义责任转给执行者；
4. **流程/接口**：输入、评审节点、样例、版本或反馈闭环是否缺失。

每个候选都要标当前置信度（低/中/高）及依据。证据不足时可以全部为低、写“当前无唯一最强解释”，但不能因此省略人物/权力候选；取得一个被接受样本、一个被拒绝样本或最近一次具体反馈后再翻转排序。判断模糊标准是否形成权力机制时，比较同一评价者跨版本、同一版本跨人是否一致，并观察用户提出校准请求后能否得到可执行标准；不能从一次含糊反馈推断对方动机。

每个候选必须包含：

```text
机制：A 怎样导致 B；中间环节是什么？
适用条件：在什么边界内成立？
辨别预测：如果成立，应看到什么；竞争解释会看到什么不同结果？
已有证据 / 反证：
可干预变量与有权者：
最小验证动作、窗口和风险：
翻转阈值：出现什么就降级或放弃该解释？
```

不要把“领导人品差”“用户不够努力”“公司有毒”当机制。它们只能是待拆词，必须落回行为、规则、重复模式和可证伪后果。

### Phase 5：选择辨别动作

优先选能最大区分首选与替代解释、成本最低、可逆且已获权限的动作。例如补一个事件账、核对政策原文、比较同流程跨人/跨期结果、向有权者校准验收正反例，或做只改变一个变量的小试验。

验证动作没有执行前，写“待验证”；外部沟通、提交、改权限或高风险试验必须另行确认。

### Phase 6：生成职场问题说明书

```text
原始困惑：
现象句与比较基线：
要完成的分析任务：解释 / 预测 / 改进 / 决策支持
核心冲突：
已确认事实及坐标：
用户目的与外部要求：
当前状态/容量（事实/推断/未知）：
人物、权力与决定链：
公司正式规则 / 实际惯例 / 本次事件：
约束、不可变项与代价承担者：
候选解释及竞争预测：
当前最强解释、置信度与反证：
反馈入口、观察窗口和安全边界：
当前可行动作与有权者：
未解决部分和会翻转判断的新证据：
```

材料不足时输出“半成品问题说明书”，只填已知项和最小补充问题；格式完整不能成为脑补许可。

## 分支规则

| 信号 | 处理 |
|---|---|
| 只有抽象评价，无具体事件 | 保留原词，索取一个正例、一个反例或最近事件；只给并列条件分支 |
| 有明确断点但证据较少 | 给 1–2 个低置信候选和区分性预测，不下主因结论 |
| 跨人、跨期重复且随流程变量变化 | 暂列共同原因候选，同时寻找个别特殊事件；用过程改变后的分布验证 |
| 单次可追踪异常 | 先处理特殊事件，不外推人格或公司规律 |
| 用户没有改变条件的权限 | 把产物改成取证、建议、协商或升级支持；不宣称条件已改变 |
| 存在报复、骚扰、违法或健康风险 | 先保护安全、证据和现实支持；停止危险实验或直接对质 |
| 只是需要准确答案或材料整理 | 作为 Question 直接交付，不强制展开人格/组织分析 |

## 理论镜头落地

每题最多使用 1–2 个镜头，并形成 `触发证据 → 观察 → 辨别动作 → 字段 → 推翻条件`。

- **波普尔**：把首选原因写成条件预测，预先列区分性反证、阈值和观察窗口。
- **戴明**：用同口径跨人/跨期分布区分共同原因与特殊原因，样本不足时只给暂定归因。
- **维特根斯坦**：当“主动、专业、支持、完成”用法漂移时，收集验收正反例并写操作定义。
- **西蒙娜·薇依**：超载和注意受损被人格化时，先做容量账，再观察减负后的错误与启动变化。

没有产生新观察、辨别动作或翻转条件时删除人物名，回到普通流程。

## 正例、反例与边界例

**正例：领导说用户“不主动”**

取得两次具体事件：一次用户没提前报告延期，一次用户发现风险但无权改排期。把“信息上行断点”和“责任大于权限”列为竞争解释；向领导校准“主动”的被接受/被拒绝案例，并记录是否存在安全表达空间。未校准前不判用户能力差。

**反例：一次冲突直接判公司压制**

用户只说“同事怼我、我也不敢提问题”，就断言结构性压制并建议越级。缺事件、重复模式、权力与报复证据时，结论和动作都越界。

**边界例：疑似报复**

若用户报告提出合规问题后被威胁降薪，不把它当普通沟通冲突做 A/B 试验。先最小化留存原始证据、检查即时安全和合适的专业/组织支持；本 Skill 只整理事实与未知，不认定法律责任。

## 现实验证与回流

现实反馈回来后：

1. 记录实际动作、执行人、日期、结果和未控制变量。
2. 分别标记每个候选为支持、削弱、未区分或无法验证。
3. 更新问题说明书，不重写原始事实；新证据与旧判断冲突时显式改口。
4. 若结果要求价值取舍，交 `xb-decision`；若形成学习缺口，交 `xb-learning`；若需长期人物/公司档案，取得授权后交对应专科。
5. 重复问题留下可复用的事件字段、验证规则或来源坐标；不得保存无关心理和隐私信息。

## 输出与完成判定

默认输出：`现象与冲突`、`证据账摘要`、`候选解释对比（逐项置信度）`、`当前最强解释或无法排序的理由`、`职场问题说明书`、`最小验证动作`、`未解决部分`。涉及模糊人物评价时，必须让词义/目标版本、真实质量/能力、人物/权力、流程/接口四类候选在输出中可见。

- 问题说明书可直接使用、候选解释可区分且反馈点明确时，只能说“分析瓶颈已有可执行干预”。
- 现实反馈已经排除关键竞争解释并达到预设阈值时，才可说“在 {时间/范围} 内，原因判断已得到支持”。
- 权力、授权、风险或关键材料缺失且会改变动作时，判“无法验证”，列精确缺口。
- 不得用无范围的“已经分析清楚”或“当前这一步完成”掩盖未发生的验证。

## 自检

是否钉住了现象而非大词？是否写出谁定义预期、谁有权、谁承担代价？是否比较了真正竞争的解释？是否主动找反证？是否把容量或结构伤害个人化？是否给出安全、可逆、可授权的现实反馈点？
