# Agent 工作责任评估

只在用户要求评估一条具体 Agent 工作流、解释责任边界、检查监督是否有效或生成责任检查卡时读取。本文件把 `xb-agency` 已有的权责对称观与行动责任观转成可填写的工作流分析；普通观点讨论继续使用 `subject-actionism.md`。

## 目标与完成标准

把“谁负责”“我为什么控制不了”推进成四项可用产物：

1. 一张按时间顺序还原的六站事实卡；
2. 结果链、信息链和控制链三张可核验记录；
3. 分轴责任判断及其证据状态；
4. 一个当前即可使用的权限、证据、复核、升级或补救动作。

本方法完成的是责任事实整理和当前判断。现实中的处分、赔偿、制度整改和关系变化仍要等待有权者行动与外部证据。

## 进入与关闭

进入信号：

- Agent 已经生成、调用、修改、发送、执行、评分或影响现实采用；
- 用户被要求确认、解释或承担 Agent 结果；
- 流程里出现“有人复核”，但复核者的信息、时间、能力、否决权或接管条件不清；
- 用户想说明哪些结果、信息和控制权属于自己，哪些分布在业务、领导、组织、部署方或提供方；
- 争议涉及责任错配、空壳监督、道德缓冲区或责任缺口。

关闭或缩短：

- Agent 只处理低风险、可撤回草稿，结果尚未采用，目标与验收都清楚：给局部责任说明即可；
- 用户只要设计自动化流程：保持 `xb-automation` 为当前专科，必要时隐藏取得责任字段；
- 争议由合同、法律、正式制度或专业标准直接决定且原文未核验：停止具体定责，保留事实卡并指出所缺原文；
- 已出现报复、违法要求、隐私泄露或重大不可逆风险：先走保护与专业升级路径。

命中低风险缩短条件时，停止展开完整六站、三链、四入口和组织论坛，只交付一张局部责任卡：

```text
当前用途与已确认输入：
Agent 当前权限与禁止动作：
采用前由谁核对，谁可修改或放弃：
权限、用途或采用方式发生哪些变化时重开完整评估：
完成范围：当前判断覆盖到哪一步，尚未覆盖哪些人工采用：
```

缩短分支最多保留以上五项。Agent 缺少外发、写系统或建任务权限，只能排除 Agent 自主执行这些动作；人工外发、转录任务或进入高影响用途仍属于采用侧变化，不能提前排除。

## 先分开两条后果线

每次先记录：

1. **直接动作线**：Agent 自己读取、生成、调用、修改、下载、发送或支付了什么；
2. **采用后果线**：哪个人或组织把 Agent 输出带进了报告、客户承诺、经营判断、人事决定、资金动作或生产环境。

Agent 停在草稿层，不代表下游采用也是低影响。Agent 没有按最后按钮，也可能通过输出参与高影响决定。

## 第一步：确认四个基本量

| 基本量 | 必须记录 |
|---|---|
| 行动能力 | Agent 客观上能观察、生成、调用、执行、纠错、停止和转交到哪一步 |
| 组织权限 | 谁允许它使用哪些账号、数据、工具、金额、对象和审批范围 |
| 责任资格 | 哪些人或组织能够解释理由、接受处分、赔偿并承担长期改正义务 |
| 身份与溯源 | 能否还原哪个实例代表谁，基于什么目标、凭证、版本和记录行动 |

四项中任一未知都要保留为未知。技术上能做无法证明组织已经授权；日志能记录动作也无法单独证明授权合理或责任归属。

## 第二步：用六站还原事实

六站按工作发生顺序填写。用户已经提供的事实直接落位；只有缺口会改变责任判断、风险或下一动作时，才补问一个最有区分力的问题。

### 定：目标、标准与权限

- 谁提出目标和用途；
- 谁定义口径、成功标准和禁止项；
- 谁决定 Agent 可以读取、写入、调用和影响什么；
- 哪些变化会触发重新确认。

### 做：Agent 的实际行动

- Agent 生成、查询、调用、修改、下载、发送或执行到哪一步；
- 使用了什么身份、账号、工具、输入和版本；
- 改变了哪些外部状态；
- 是否出现扩权、跨系统、再委托或计划漂移。

### 审：实质复核

- 谁做首轮验证，谁在何种变化下独立复核；
- 复核者看见了哪些证据，哪些过程不可见；
- 是否具备时间、知识、否决、暂停、改写、退回与接管条件；
- 纸面复核者和实际复核者是否一致。

有姓名、岗位或确认按钮只证明流程里安排了人。信息、时间、能力、权力和支持至少缺一项时，监督资格要标记为不足或待核验。

### 用：每一段采用

- 谁采用了哪项 SQL、文件、结论、建议或评分；
- 每次采用用来决定什么，影响谁；
- 采用者能看见、理解和改变哪些部分；
- 谁拥有拒绝、延迟或限制采用的权力。

一条工作流可以出现多次采用。每位采用者只对其实际判断、知识和控制范围进入责任评估。

### 救：停止、修复与补救

- 技术故障由谁重试、修复或回滚；
- 业务口径、数据质量、模型缺陷和制度问题分别交给谁；
- 谁能调取证据、暂停影响、通知受影响者、纠正结果和提供资源；
- 当前保留哪些手动作业、异常演练和恢复能力。

角色名称要与证据权、接管权和补救资源一起记录。只有名称时标记为纸面角色。

### 分：收益、信用、成本与风险

- 节省的时间和新增产量流向谁；
- 工作信用、绩效和学习收益计入谁；
- Token、复核、维护和训练成本由谁支付；
- 返工、解释、声誉、处分和错误损失由谁承受；
- 投入是否自愿，是否保留停止和重新协商空间。

分配失衡是继续检查权力与制度的信号。它无法单独证明某条责任轴已经出现缺口。

## 第三步：生成三条证据链

### 结果链

记录目标如何经过 Agent 动作、人工修改、验证和采用变成当前结果。回答“结果怎样产生”。

### 信息链

逐角色记录在关键时点知道什么、能合理知道什么、看不到什么。回答“谁在当时掌握哪些信息”。

### 控制链

逐环记录谁能决定、授权、拒绝、暂停、改写、采用、回滚、调证和补救。回答“谁能改变过程或后果”。

每个落位使用四种证据状态：`题面事实 / 用户解释 / 推断 / 待核验`。Agent 只协助整理它可访问且有记录的部分；口头决定、隐藏上下文、组织动机和实际权力没有证据时保持待核验。

## 第四步：用“怪、说、审、管”分轴判断

四个入口采用 `1 个资格状态 + 2 种问责关系 + 1 项治理任务` 的结构。

### 怪：可责性

逐个候选者检查其在关键时点是否具备足够知识、控制和选择空间。缺少拒绝权只会降低或排除该候选者，责任搜索还要继续覆盖业务、管理者、数据方、部署方、提供方和组织角色。

### 说：面向受影响者说明理由

检查谁有义务说明目标、依据、动作、验证、采用和补救理由，并回应具体质疑。该关系可以发生在业务、员工、客户、领导或其他受影响者之间。

### 审：接受有权论坛审查

论坛至少要能要求回应、调取关键证据、询问相关角色、作出判断并要求纠正或施加后果。只有聊天、旁观或建议权时，记录为沟通载体或空壳论坛。

### 管：事前与持续治理

检查谁拥有角色、权限和资源来设定边界、建设能力、持续监测、演练接管、处理变化并修改制度。事故中无人值得责备时，未来治理任务仍可存在。

## 第五步：识别结构状态

| 状态 | 判断条件 | 输出动作 |
|---|---|---|
| 可治理委托 | 目标清楚、权限有界、身份可验、过程可追、监督有效、异常可停、结果可救 | 保留流程，记录局部责任和变化触发器 |
| 责任错配 | 某条轴存在合格承担者，责任却压向低知识、低控制或低选择者 | 重画责任分配，补权力、资源与书面决定 |
| 空壳监督 | 设有人工复核，复核者看不见、看不懂、来不及、拦不住或接不回 | 降低行动强度，补证据、否决和接管条件 |
| 道德缓冲区 | 最可见或最近的操作员吸收主要责备，实际决定、收益和控制位于上游 | 显形实际权力与成本流向，阻断单点追责 |
| 分轴责任缺口 | 指定责任轴、确定资格门槛、搜索完整链以后仍无合格承担者 | 明确缺口轴，设计新的承担角色或制度接口 |

判断责任缺口必须完成四步：`指定责任轴 → 确定门槛 → 搜索完整责任链 → 无人满足`。“大家都说不知道”、一个人无拒绝权或一个群没有处置权，都只提供局部证据。

## 第六步：设置变化触发器

以下任一变化出现时，暂停当前默认规则，重新检查至少受影响的六站：

- 目标、口径、成功标准或结果用途变化；
- 参与者、验证者、采用者或受影响对象变化；
- 数据、表、字段、模型、提示、工具、接口或版本变化；
- 账号、权限、金额、外发范围或再委托能力变化；
- 异常信号、错误后果、可逆性或影响人数变化；
- 强制使用、收益归属、错误成本或申诉条件变化。

变化只触发重新判断，不自动推出停止、升级或增加复核。下一动作由后果、可逆性、证据和现实权力共同决定。

## 竞争解释与辨别

至少保留一个会导向不同动作的解释：

| 表面现象 | 候选解释 A | 候选解释 B | 最小辨别证据 |
|---|---|---|---|
| 最后由员工确认 | 员工拥有充分信息与自由否决 | 确认只是空壳监督 | 时间、证据、能力、拒绝与接管权 |
| Agent 结果出错 | 使用者绕过已知警告 | 口径、数据、配置或组织期限造成 | 警告记录、口径版本、数据告警、期限决定 |
| 没人能解释 | 证据尚未集中整理 | 过程缺少记录或论坛无调证权 | 日志范围、记录 owner、论坛权力 |
| 公司获益、个人付费 | 用户自愿投资并获得可支配收益 | 组织强制使用并转移成本 | 强制程度、停止权、收益与成本变化 |

## 正例、反例与边界例

**正例：受限数据草稿。** Agent 只生成查询草稿，员工拥有审核和提交权，业务拥有口径与结果采用权；新口径或新数据结构触发重新确认。输出局部责任卡，不强制建立完整组织论坛。

**反例：一次确认等于全责。** 员工只看见最终数字，缺少完整上下文、核验时间、退回和拒绝权。组织把点击确认视为完整责任。应标记监督资格不足，继续追踪口径、期限、采用、证据和补救权，禁止把责任搜索停在员工。

**边界例：管理型 Agent 处分员工。** Agent 评分并影响绩效，员工看不到依据，日志由供应商和人力控制。先要求保全证据、暂停不可逆后果、开放信息和独立复核；具体法律义务等待制度原文与专业核验。

## 验证与回流

- **产物验证**：六站、三链和四个责任入口能否逐项指向证据状态；
- **行动验证**：先写用户当前有权执行的动作，再写有授权权角色应执行的组织动作；两者不得合并成一句。用户没有配置论坛、授予调证权或命令更正的权限时，用户动作限于保全记录、提出书面请求、申请复核、拒绝个人归责或选择是否升级；设立论坛、授予权力和配置资源必须落到具备授权权的管理者或组织角色；
- **失败信号**：责任结论仍只看账号、角色名或确认动作；理想复核者被写成当前事实；Agent 替未知组织信息补故事；分配失衡被直接写成责任缺口；
- **翻转**：新证据改变知识、控制、选择、论坛权力、采用后果或自愿性时，重算受影响的责任轴；
- **完成范围**：检查卡与当前判断可以在本轮交付，现实流程改善要等待权限、制度、复核或补救结果回流。

## 自检

- 是否先还原直接动作和采用后果，再分配责任？
- 是否区分事实、用户解释、推断和待核验？
- 是否把一个候选者不达标误写成整条责任轴的缺口？
- 是否把群聊、签字或名义复核误写成实质监督？
- 是否显形 Agent 的可见范围与证据边界？
- 是否让用户获得一份可使用的检查卡和当前动作？
- 是否保留用户对拒绝、升级、申诉、签署和其他高风险动作的决定？
